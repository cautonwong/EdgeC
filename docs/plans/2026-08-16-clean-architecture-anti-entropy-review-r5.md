## 0. 总判定

**V5 是合格的可执行版，评级从四审的 C+ 提升到 B+。** 可批准“Phase 0 + Phase 1 共 11 个 Ticket”先行执行；但仍有 **5 个缺口**必须在 Phase 2 开启前补上：

1. ADR-0008 本体未同步（仍是原版，状态 Accepted，且未含长期治理机制）；
2. AEP-001 默认“原子 Commit”25+ 个未审 WIP，把用户决策偷换成既定动作；
3. AEP-352 的 TagID 十六进制分域方案与现有 1001/2001/12001 体系冲突，缺迁移兼容策略；
4. 完全缺失行业合规/认证维度（IEC 62304/62443、GDPR/PIPL、OpenHarmony、MISRA）；
5. 缺需求→设计→测试的可追溯性（Traceability），15 年认证类产品绕不开。

## 2. 剩余关键问题（5 项）

### 2.1 ADR-0008 本体未同步（高）

主计划已进化到 V5，但 `docs/adr/0008` 仍是原始章程：状态 `Accepted`、日期 2026-08-15、无 Phase 5 长期治理、无“修订 ADR-0005 部署位置”的说明。

建议：新增 `AEP-511`：**ADR-0008 V2 修订**——状态改 `Proposed`、补长期治理附录、写明与 ADR-0005/0007 关系、版本化（V1→V2），并经 Mr. WKT 批准后置 `Accepted`。

### 2.2 AEP-001 把“提交 WIP”当成既定动作（高）

原文：“将 DCU/IEMS/edge_bsp_hal 等 25+ 文件做原子 Commit”。

这些文件从未评审，可能包含半成品/实验代码。应改为三选一由 Mr. WKT 决策：**A=全部提交为 WIP 基线；B=仅提交评审过的；C=移出工作区冻结**。Ticket 的 DoD 应为“按决策结果执行 + 基线 tag”，而不是默认提交。

### 2.3 TagID 分域方案与现状冲突（高）

AEP-352 建议 `0x01xxxx` DCU、`0x02xxxx` IEMS、`0x03xxxx` SmartBox。但现状是：

- IEMS/SmartBox 共用 1001/2001/12001 体系；
- DCU 已混用 536871424 等 Hex OAD；
- 现有数据库、契约、Go 常量全部依赖当前 ID。

直接重编号 = 破坏性迁移。建议：**新增域只对新 Tag 生效；存量 Tag 建立“旧域别名映射”，并提供编译器自动迁移/校验规则**（如 `legacy_aliases.yaml`）。AEP-352 的 DoD 应增加“存量契约零破坏迁移证明”。

### 2.4 行业合规/认证维度缺失（高，15 年目标的关键）

仓库文档已出现 GDPR/PIPL、IEC 61850、IEC 62443、OpenHarmony 认证等诉求，但主计划 **0 项合规任务**。15 年生命周期里，医疗（SmartBox）和电力（DCU）产品必然面对：

| 标准/法规 | 适用对象 | 计划缺失点 |
|---|---|---|
| IEC 62304（医疗软件生命周期） | SmartBox/医疗 | 无需求追踪、无变更管理、无软件安全分类 |
| IEC 62443（工业网络安全） | DCU/IEMS | 无安全等级目标、无 SBOM 门禁、无安全回归基线 |
| IEC 61850/电力规约 | DCU | PRD 有愿景，无一致性测试策略 |
| GDPR / PIPL | SmartBox | 有实现，无合规映射与审计证据链 |
| OpenHarmony 认证 | SmartBox | 发布说明提到送检，无认证基线管理 |
| MISRA C:2012 | 全平台 | CI 无 MISRA 强制检查 |

建议新增 `AEP-512`：**合规矩阵与认证基线**（每产品一页：适用标准→等级目标→对应 AEP/测试→证据）；`AEP-513`：**需求追踪矩阵（RTM）工具**（需求→设计→测试→证据，至少覆盖认证类产品）。

### 2.5 性能/资源预算缺失（中）

只定义了 150KB 尺寸不变量，但没有运行期预算：延迟、内存峰值、CPU、吞吐（10kHz 采样、2000 表抄读）。15 年演进中“纯内核”重构极易悄悄增加时延。

建议 `AEP-514`：**性能基线门禁**——关键路径基准（DataHub 写读延迟、Ring 吞吐、SQLite 批写、WASM tick）进 CI，重构前后对比。
