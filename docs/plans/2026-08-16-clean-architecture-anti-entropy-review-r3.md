# Codex 三审：15 年防腐化路线图 —— 多角色、多时间尺度推演

> **Mr. WKT** — 评审目标：以“多人多项目、跨 10~15 年超长生命周期防代码腐化（Anti-Entropy / 防成为屎山）、二开方便”为唯一验收标尺。
> 方法：代入 9 个真实角色，把 ADR-0008 + 反熵主计划放到 1/3/5/10/15 年后的世界去推演，并做“屎山生成器”对抗性测试。

---

## 0. 总判定（先给结论）

**这份计划能防住“第 1~2 年的屎山”，但防不住“第 3~15 年的屎山”。**

它解决的问题是真实的（依赖倒挂、双重源码树、手工 extern 注册、无二开脚手架），方案方向也正确；但它把所有治理能力都押在“一次性重构 + CI 全绿”上，缺少**时间维度上的治理机制**：API 兼容策略、生成物可信链、SDK 版本与 LTS、熵指标与年度审计、知识传承、工具链 EOL 预案、二开升级路径。

结论：**批准架构方向；把“长期治理机制”作为独立章节（建议 Phase 5 / Charter 附录）补进计划；执行上仍按“先 Phase 0/1，逐阶段验收”。**

## 2. 时间尺度推演：什么会活下来，什么会腐烂

### T0：第 1~2 年（重构执行期）

**活下来的**：基线 tag、clean build、134/134 + 10/10、edge-cli、生成式注册表、Out-of-Tree SDK。

**腐烂风险**：
- 未提交 WIP（DCU daemon/fusion）与重构混在一起 → 基线漂移；
- CI “ASan/TSan 矩阵加了但覆盖参数还是错的” → 表演式全绿；
- Phase 2 直接搬 35 个 sqlite 依赖文件 → 符号/时序回归。

**这一阶段的成功标准**：不是“重构完成”，而是“**任何人都能 30 分钟内从 clone 到跑通 demo，且改动核心代码的 PR 会被 CI 拒绝**”。

### T1：第 3~5 年（多产品并行期）

**活下来的**：目录边界、生成式注册、lint、模板。

**腐烂风险**：
- Tag 命名空间开始撞车（T-202 若没落地，SmartBox 和 DCU 迟早同名不同义）；
- SDK 1.x/2.x 并存，二开项目各自锁版本，上游修复下不去；
- 生成物被手改、编译器升级后输出漂移，没人发现；
- 新团队绕过脚手架，“图快”直接改核心，CI 只读门禁被管理员放行。

**必须有的机制**：语义化版本 + 兼容矩阵 + 生成物指纹 + CODEOWNERS + 只读门禁不可豁免（豁免必须留痕）。

### T2：第 6~10 年（依赖 EOL 与技术换代期）

**腐烂风险**：
- Python/CMake/Node 工具链版本 EOL，CI 开始“昨天还能跑”；
- CycloneDDS/QuickJS/WAMR 上游换代，ABI 变化；
- 新硬件平台（MCU 升级）要求 edge_core 真·轻量化，150KB 目标变成硬约束；
- 老设备固件停留在旧 SDK，现场无法升级。

**必须有的机制**：工具链容器化/锁定、依赖 EOL 日历、LTS 分支、设备升级矩阵、ABI golden test。

### T3：第 10~15 年（团队换血期）

**腐烂风险**：
- 初始团队大量离开，隐性知识只剩 ADR 和“当年某个人说的”；
- 测试全绿但没人敢动：覆盖率变成“覆盖容易的代码”；
- ADR 与实现脱节：0005 与 0008 的矛盾无人清理；
- 二开项目 fork 成家族，上游 EdgeOS 变成“理论上的上游”。

**必须有的机制**：熵指标（复杂度/耦合/重复/TODO 密度/CI 红时长）、年度防腐审计、可复现构建（含 10 年前 tag）、知识传承制度（轮岗、playbook、决策记录）。

## 3. “屎山生成器”对抗性测试（10 个场景）

| # | 场景 | 计划能挡住吗 | 缺口 |
|---|---|---|---|
| 1 | 二开图快直接改 SDK 核心 | 部分 | 需要 CI 只读门禁 + 上游 merge 保护（CODEOWNERS + 不可豁免） |
| 2 | 新驱动靠复制粘贴注册 | ✅（生成式注册表） | 需要模板 + lint 强制走 YAML |
| 3 | Tag 同名不同义泛滥 | ❌ | T-202 必须进 Phase 3.5，且 validator 全局查重 |
| 4 | 生成代码被手改 | ❌ | 生成物指纹 + CI 重生成 diff |
| 5 | CI 变“表演式全绿” | ❌ | 门禁抽查 + 变异测试 + 失败样本复盘 |
| 6 | 老产品锁死旧 SDK | ❌ | LTS + 兼容矩阵 + migration CLI |
| 7 | 供应商 HAL 升级破坏适配层 | ✅（非侵入原则） | 需要适配层回归测试 + module.yml 版本锁定 |
| 8 | 15 年间安全补丁不断 | ❌ | SBOM + 安全扫描 + 密钥轮换（T-001）入治理 |
| 9 | 文档与代码脱节 | ❌ | docs-as-code + ADR 一致性检查 |
| 10 | 总线因子=1（关键人物离职） | ❌ | 决策记录 + 可复现构建 + 轮岗 |

结论：**计划目前只挡住 2/10，另外 8 个需要在“长期治理机制”章节补**。

## 4. 二开便利性专项推演（DX）

### Persona A：产品工程师（新建储能产品）

理想路径：`edge-cli create-product bess --template=iems` → 改 YAML → `edge-cli lint-contract` → 编译 → 跑 demo。

推演出的摩擦点：
- 依赖安装（CMake、.local、.venv、Go）没有一键引导；
- 模板内容 = 当前 iems 的快照，3 年后会过时；
- SDK 升级时没有迁移工具；
- 许可说明缺失（他要向客户交付）。

### Persona B：驱动工程师（新增液冷驱动）

理想路径：`create-driver --proto=modbus` → 填 ops → YAML 声明 → 注册表自动生成。

推演出的摩擦点：
- 生成式注册表依赖编译器规则，文档必须写“注册失败怎么排查”；
- 驱动需要单元测试模板，否则“能注册”≠“能工作”。

### Persona C：算法工程师（新增 WASM Stage）

理想路径：Stage 模板 + 沙箱 API + 签名链。

推演出的摩擦点：
- 沙箱签名密钥（T-001）没解决前，App Store/OTA 是空谈；
- WASM 失败回退假值问题（R2/R3 已指出）不修，二开算法会“看起来能跑但数据是假的”。

### 升级场景（最重要）

二开项目最痛的不是第一次接入，而是 **SDK 1.x → 2.x 时全量迁移**。计划必须包含：
- `edge-cli migrate`（扫描旧 API、契约、CMake 引用并自动改写）；
- 兼容层保留期策略（如：破坏性变更至少提前 2 个版本 Deprecation）；
- 每个 SDK 版本一份“破坏性变更清单”。

## 5. 必须补入计划的“长期治理机制”（Phase 5 / Charter 附录）

1. **ADR 生命周期治理**：Proposed → Accepted → Superseded；每年一次“ADR-实现一致性”审计。
2. **API/ABI 兼容政策**：语义化版本；`PipeMsg` 64B、`edge_tag_meta_t`、ops 虚表的 golden header 测试；ABI 断裂 = 大版本。
3. **生成物可信链**：所有生成物（contracts.c/tags.go/注册表/IDL）带“AUTO-GENERATED”头 + CI 重生成比对；手改 = 构建失败。
4. **熵指标与年度审计**：复杂度、模块耦合、重复代码、TODO/FIXME 密度、CI 红时长、生成物漂移次数；每年产出一份《防腐健康报告》。
5. **代码所有权**：CODEOWNERS 按模块分配；核心目录修改需双人评审且门禁不可静默豁免。
6. **LTS 与支持矩阵**：哪个 SDK 版本支持到哪一年；老设备固件升级路径；回滚策略。
7. **工具链 EOL 预案**：容器化构建镜像 + 依赖 EOL 日历；10 年后仍可复现 10 年前的 tag。
8. **安全治理管线**：SBOM、依赖漏洞扫描、密钥轮换、安全回归基线（重构前后对比）。
9. **知识传承制度**：CONTEXT-MAP/glossary 强制维护、Playbook、轮岗、决策记录（ADR 必须回答“为什么不是另一个方案”）。
10. **防表演式全绿**：覆盖率阈值按“核心文件”而非总量；定期变异测试抽查；CI 红必须 48h 内处理。

## 7. 最终判定与批准建议

**判定**：ADR-0008 + 反熵主计划是合格的“第一年防腐化路线图”，但不是完整的“15 年防腐化宪章”。

**批准建议**：
1. 批准架构方向（四层洋葱、纯内核、端口适配器、生成式注册、Out-of-Tree）；
2. 把“长期治理机制”（§5 的 10 项）并入 ADR-0008 作为 Phase 5 / 附录，再正式 Accepted；
3. 执行顺序不变：Phase 0（基线冻结）→ Phase 1 → 逐阶段验收；
4. 二开便利性的验收标准定为：**一个全新产品工程师，从 clone 到跑通 demo ≤ 30 分钟；SDK 升级时，`edge-cli migrate` 一次通过**。
