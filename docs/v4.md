# 第一章：核心架构与生命周期管理 (Architecture & Lifecycle)

本章重点研究 `device-sdk-c` 如何把一个复杂的设备接入服务抽象成通用的流程，以及我们如何将其改良以适配 Linux 嵌入式环境。

## 1. EdgeX 源码深度剖析 (Deep Dive)

### 1.1 "IoC" (控制反转) 架构
在 `src/c/service.c` 中，EdgeX 并不让驱动去写 `main` 函数，而是 SDK 提供 `main`，驱动只提供回调。

*   **EdgeX 做法**：
    它定义了一个核心结构体 `devsdk_service_t`（服务实体）和一个接口结构体 `devsdk_impls_t`（驱动实现）。
    *   开发者只需要实现 `init`, `discover`, `get_handler`, `put_handler`, `stop` 这五个函数。
    *   SDK 负责启动 HTTP Server，监听配置中心，管理线程池。
*   **借鉴价值**：
    这种**“填空题”式开发体验**非常好。它强制分离了“通用逻辑”（SDK）和“业务逻辑”（驱动）。

### 1.2 配置管理 (Configuration Watcher)
在 `src/c/config.c` 和 `src/c/watcher.c` 中。
*   **EdgeX 做法**：
    它不仅读取本地 TOML/JSON，还连接 Consul/Keeper 配置中心。最精髓的是它实现了 **Watcher 模式**：
    *   当云端修改配置（如修改了轮询间隔），SDK 收到回调，自动更新内存中的配置，并触发驱动的 `reconfigure` 回调。
    *   实现了 **Read-Write Lock** 保护配置对象，防止在读取配置时发生更新导致的崩溃。

### 1.3 `iot_data_t` 通用数据容器
在 `src/c/iot_data.c` 中。
*   **EdgeX 做法**：
    这是 EdgeX 的万能数据类型，类似于 Python 的 `dict` 或 JSON 对象。它可以存 Int, Float, String, Binary, Map, Array。
    *   驱动读取的数据先封装成 `iot_data_t`，再交给 SDK 处理。
*   **借鉴价值**：
    虽然我们的 `DataPoint` (32字节) 对时序数据更高效，但在**配置参数传递**、**复杂命令下发**（如设置一组参数）时，`iot_data_t` 这种动态类型的灵活性是必须的。

## 2. 吸收与改良 (Synthesis & Refactoring)

针对 **SG-EL2025** 和 **(H/I)EMS** 场景，我们对 EdgeX 的设计进行“嵌入式化”改造。

| 模块 | EdgeX (原版) | EdgeOS SDK (改良版) | 理由 |
| :--- | :--- | :--- | :--- |
| **通信机制** | REST API (Microservice) | **ZeroMQ / shm_ring** (IPC) | 消除 HTTP 开销，适配实时控制 |
| **配置中心** | Consul (HTTP Long Poll) | **Inotify (File Watch)** | 嵌入式设备通常由文件配置，去中心化 |
| **线程模型** | `iot_threadpool` (Pthread) | **`libuv` Event Loop** | 减少上下文切换，统一异步模型 |
| **驱动接口** | `get/put_handler` (字符串键) | **`read/write_tag` (TagID 键)** | 字符串匹配太慢，TagID 哈希最快 |

## 3. 新设计文档：Service 核心 (Service Core)

### 3.1 核心结构体定义

我们吸取 EdgeX 将 `impl` (实现) 与 `service` (服务) 分离的精华。

**文件:** `include/edge_service.h`

#define EDGE_SERVICE_H

typedef struct {

    char *name;
    char *version;
    
    // 运行时上下文 (libuv loop, db, bus)
    EdgeContext *ctx; 
    
    // 驱动实现方法的指针

### 3.2 配置文件热重载机制 (Config Hot-Reload)

EdgeX 依赖 Consul 做动态配置。我们在 Linux 嵌入式上利用 `libuv` 的 `uv_fs_event` 监控 JSON 文件变化，实现同样的效果，但不需要部署 Consul。

**文件:** `src/core/config_watch.c`

```c
#include "edge_service.h"
#include <cJSON.h>

// 读取并解析 JSON 配置文件
static iot_data_t* _load_config_file(const char *path) {
    // ... fread ... cJSON_Parse ...
    // 将 cJSON 转为 iot_data_t (Map)
    return config_map;
}

// 文件变化回调 (当用户修改了 config.json)
static void _on_config_change(uv_fs_event_t *handle, const char *filename, int events, int status) {
    edge_service_t *svc = (edge_service_t *)handle->data;
    
    printf("[Config] File %s changed, reloading...\n", filename);
    
    // 1. 重新加载
    iot_data_t *new_conf = _load_config_file(handle->path);
    if (!new_conf) return;

    // 2. 对比差异 (Diff) - 可选优化
    
    // 3. 更新缓存 (需加锁或在主线程单线程操作)
    iot_data_free(svc->config_cache);
    svc->config_cache = new_conf;

    // 4. 通知驱动 (借鉴 EdgeX 的 reconfigure)
    if (svc->ops.reconfigure) {
        svc->ops.reconfigure(svc->driver_user_data, new_conf);
    }
}

// 启动监控
void edge_config_watch_start(edge_service_t *svc, const char *path) {
    // 初始加载
    svc->config_cache = _load_config_file(path);
    
    // 启动 libuv fs event
    uv_fs_event_init(svc->ctx->loop, &svc->config_watcher);
    svc->config_watcher.data = svc;
    uv_fs_event_start(&svc->config_watcher, _on_config_change, path, 0);
}
```

### 3.3 驱动实现的样板代码 (Driver Template)

以 **Modbus 驱动** 为例，展示如何填充这个框架。

**文件:** `drivers/modbus/main.c`

```c
#include "edge_service.h"
#include <modbus.h>

typedef struct {
    modbus_t *ctx;
    int baud_rate;
    // ...
} my_driver_t;

// 1. 实现 Init
static bool my_init(void *impl, EdgeContext *ctx, iot_data_t *config) {
    my_driver_t *d = (my_driver_t*)impl;
    
    // 从 config Map 中获取配置
    const char *device = iot_data_string_map_get_string(config, "device");
    d->baud_rate = iot_data_string_map_get_int(config, "baud_rate");
    
    d->ctx = modbus_new_rtu(device, d->baud_rate, 'N', 8, 1);
    modbus_connect(d->ctx);
    return true;
}

// 2. 实现 Read
static iot_data_t* my_read(void *impl, const char *dev, const char *res, iot_data_t *protocols) {
    my_driver_t *d = (my_driver_t*)impl;
    
    // 从 protocols 获取 Modbus 地址信息 (由 SDK 传入)
    int addr = iot_data_string_map_get_int(protocols, "Address");
    int len = iot_data_string_map_get_int(protocols, "Length");
    
    uint16_t tab_reg[64];
    modbus_read_registers(d->ctx, addr, len, tab_reg);
    
    // 封装返回
    return iot_data_alloc_i16(tab_reg[0]);
}

// 3. 实现 Reconfigure (热更)
static void my_reconfigure(void *impl, iot_data_t *new_config) {
    my_driver_t *d = (my_driver_t*)impl;
    int new_baud = iot_data_string_map_get_int(new_config, "baud_rate");
    
    if (new_baud != d->baud_rate) {
        printf("Driver: Updating baud rate to %d...\n", new_baud);
        modbus_close(d->ctx);
        modbus_set_baudrate(d->ctx, new_baud); // 假设有此API
        modbus_connect(d->ctx);
        d->baud_rate = new_baud;
    }
}

// 4. 定义 Ops
static driver_impl_t my_ops = {
    .init = my_init,
    .read = my_read,
    .write = NULL,
    .reconfigure = my_reconfigure
};

// 5. 主函数 (极简)
int main(int argc, char **argv) {
    my_driver_t d;
    EdgeContext *ctx = edge_new("config.json");
    edge_service_t *svc = edge_service_create("modbus-service", my_ops, &d);
    
    // 注入上下文
    svc->ctx = ctx; 
    
    return edge_service_run(svc);
}
```

# 第二章：设备模型与资源映射 (Device Profile & Mapping)

本章重点：如何设计一套配置系统，让你的 C SDK 既能像 EdgeX 一样灵活（通过配置文件接入新设备），又能保持嵌入式所需的极致性能（消除字符串匹配开销）。

## 1. EdgeX 源码深度剖析

### 1.1 Device Profile 的设计哲学
在 `src/c/profiles.c` 和 YAML 定义中，EdgeX 将设备抽象为三层：

1.  **DeviceResource (物理属性)**：描述协议层细节。
    *   *例如*：Modbus Register 4001, Type=Int16。
2.  **DeviceCommand (逻辑属性)**：描述读写操作。
    *   *例如*：`get_voltage` 操作对应读取 `Voltage_Phase_A` 资源。
3.  **CoreCommand (北向接口)**：云端看到的 API。

### 1.2 属性（Attributes）的泛型化
EdgeX 使用 `nvpairs` (Name-Value Pairs) 来存储协议属性。
*   **优点**：通用。Modbus 驱动存 "PrimaryTable", BLE 驱动存 "UUID"。
*   **缺点 (C语言视角)**：它是基于字符串链表的查找 (`attributes.get("Address")`)。在 IEMS 高频采集（如 20ms 一次）场景下，每次采集都遍历链表查字符串，**CPU 开销巨大**。

### 1.3 数据变换 (Transform)
EdgeX 支持简单的 `base`, `scale`, `offset` 变换。
*   逻辑：`Value = (Raw * scale) + offset`。
*   局限：无法处理复杂逻辑（如 `if (val > 1000) val = 0`）。

---

## 2. 吸收与改良：针对 EdgeOS 的优化设计

针对 **SG-EL2025** 和 **IEMS** 场景，我们不能照搬 EdgeX 的字符串查找机制，必须进行 **“静态化”** 和 **“数值化”** 改造。

| 特性 | EdgeX (原版) | EdgeOS SDK (改良版) | 核心理由 |
| :--- | :--- | :--- | :--- |
| **Profile 格式** | YAML 文件 | **JSON -> SQLite** | 数据库查询比文件解析快，且支持 SQL 关联 |
| **资源索引** | 字符串名 ("Voltage") | **TagID (uint32)** | 运行时 `Hash Map` 或数组索引，O(1) 访问 |
| **属性存储** | String Map | **Struct / Union** | 消除字符串解析，直接内存访问 |
| **数据变换** | 简单线性变换 | **TinyExpr 表达式** | 支持复杂非线性校准 |

## 3. 新设计文档：Profile Engine

### 3.1 数据结构：从“泛型”到“强类型”

我们在内存中定义高效的 C 结构体，用于运行时快速访问。

**文件:** `include/edge_profile.h`

```c
#ifndef EDGE_PROFILE_H
#define EDGE_PROFILE_H

#include <stdint.h>
#include "tinyexpr.h" // 引用之前的表达式引擎

// 协议特定的属性 (使用 Union 节省空间)
// EdgeX 用 Map<String, String>，我们用具体的 Struct
typedef struct {
    uint8_t protocol_type; // 0=Modbus, 1=IEC104, 2=DLMS
    union {
        struct {
            int slave_id;
            int reg_addr;
            int reg_type;  // HOLDING, INPUT
            int val_type;  // UINT16, FLOAT32...
        } modbus;
        
        struct {
            int ca;        // 公共地址
            int ioa;       // 信息对象地址
            int type_id;   // 遥测/遥信类型
        } iec104;
        
        struct {
            char obis[16]; // "1.0.1.8.0.255"
            int class_id;
            int attr_id;
        } dlms;
    } attr;
} protocol_attr_t;

// 资源定义 (对应 EdgeX 的 DeviceResource)
typedef struct {
    uint32_t tag_id;       // 核心索引键
    char *name;            // "PhaseA_Voltage"
    
    // 1. 怎么读？(协议属性)
    protocol_attr_t proto;
    
    // 2. 怎么算？(数据变换)
    // 替换 EdgeX 的 scale/offset，使用 TinyExpr
    te_expr *transform_expr; 
    char *transform_str;   // "x * 0.1 + 5"
    
    // 3. 缓存值 (用于去重上报)
    double last_val;
    uint64_t last_ts;
} device_resource_t;

// 设备对象 (对应 EdgeX 的 Device)
typedef struct {
    char *id;              // "dev-001"
    char *profile_name;    // "meter-3phase-v1"
    
    // 驱动上下文指针 (指向具体的 Modbus/DLMS 连接对象)
    void *driver_handle;   
    
    // 资源列表
    int resource_count;
    device_resource_t *resources;
} edge_device_t;

#endif
```

### 3.2 核心流程：Profile 加载与编译

EdgeX 是每次启动解析 YAML。我们设计一个 **"Profile Compiler"** 机制：
1.  用户上传 JSON/YAML。
2.  SDK 解析并存入 **SQLite** (`metadata` 表)。
3.  SDK 启动时，从 SQLite 读取并在内存中构建 `edge_device_t` 结构体，**同时预编译 TinyExpr 表达式**。

**文件:** `src/core/profile_loader.c`

```c
#include "edge_profile.h"
#include "edge_context.h" // 引用 ctx->db

// 从数据库加载设备及其 Profile
edge_device_t* edge_load_device(EdgeContext *ctx, const char *dev_id) {
    edge_device_t *dev = calloc(1, sizeof(edge_device_t));
    // 1. 查询 device 表...
    
    // 2. 查询 resources 表 (关联 profile)
    const char *sql = 
        "SELECT r.tag_id, r.name, r.protocol_json, r.transform "
        "FROM resources r "
        "JOIN devices d ON r.profile_id = d.profile_id "
        "WHERE d.id = ?";
    
    sqlite3_stmt *stmt;
    sqlite3_prepare_v2(ctx->db, sql, -1, &stmt, NULL);
    sqlite3_bind_text(stmt, 1, dev_id, -1, SQLITE_STATIC);

    // 遍历结果集，构建内存对象
    while (sqlite3_step(stmt) == SQLITE_ROW) {
        // ... realloc dev->resources ...
        device_resource_t *res = &dev->resources[i];
        
        res->tag_id = sqlite3_column_int(stmt, 0);
        
        // 解析 Protocol JSON 到 C Struct (消除运行时的字符串解析)
        const char *proto_json = sqlite3_column_text(stmt, 2);
        _parse_proto_json_to_struct(proto_json, &res->proto);
        
        // 预编译数学公式
        const char *expr_str = sqlite3_column_text(stmt, 3);
        if (expr_str) {
            // 绑定变量 'x'，运行时只需更新 x 的值即可求值
            // 注意：这里需要配合线程局部存储或每次求值上下文
            res->transform_expr = te_compile(expr_str, vars, 1, 0);
        }
    }
    
    return dev;
}
```

### 3.3 运行时：极速读取流程 (The Fast Path)

这是相对于 EdgeX **最大的性能提升点**。

*   **EdgeX 流程**：
    `HTTP Request` -> `Find Device (String)` -> `Find Resource (String)` -> `Read` -> `Transform` -> `JSON Response`.
*   **EdgeOS SDK 流程**：
    `Timer Trigger` -> `Iterate Resources (Array)` -> `Driver Read (Struct)` -> `TinyExpr Eval` -> `shm_ring`.

**文件:** `src/core/data_engine.c`

```c
// 处理从驱动读回来的原始数据
void edge_process_raw_data(edge_device_t *dev, device_resource_t *res, void *raw_data) {
    double val;
    
    // 1. 根据协议类型提取原始值 (如 Modbus uint16 -> double)
    if (res->proto.protocol_type == PROTO_MODBUS) {
        uint16_t *reg = (uint16_t*)raw_data;
        val = (double)*reg;
    }
    
    // 2. 执行变换 (TinyExpr)
    // 相比 EdgeX 的线性变换，这里支持任意逻辑
    if (res->transform_expr) {
        // 更新绑定的变量 'x'
        // te_variable x = {"x", &val}; ...
        val = te_eval(res->transform_expr);
    }
    
    // 3. 死区过滤 (Deadband) - EdgeX 也有此功能
    if (abs(val - res->last_val) < 0.001) {
        return; // 没变化，不上报
    }
    
    // 4. 推送至总线
    DataPoint dp = { .tag_id = res->tag_id, .ts = now(), .val.f = val };
    shm_ring_push(ctx->bus, &dp);
    
    res->last_val = val;
}
```

## 4. 关键借鉴点总结 (Takeaways)

通过研究 `device-sdk-c` 的 Profile 设计，我们为 EdgeOS SDK 确立了以下原则：

1.  **元数据驱动 (Metadata Driven)**：
    代码里不应该出现 `if (addr == 4001)`。所有的地址、类型、公式都必须在 **Profile** 中定义。SDK 只是一个执行 Profile 逻辑的虚拟机。

2.  **读写分离 (Command Segregation)**：
    借鉴 EdgeX，将 **Resource (原子点)** 和 **Command (组合动作)** 分离。
    *   在 IEMS 中，这就是 **遥测 (Telemetry)** 和 **遥控 (Control)** 的区别。
    *   我们在 SDK 中应提供 `read_resource()` 和 `execute_command()` 两个独立的 API 入口。

3.  **协议参数结构化**：
    EdgeX 为了通用性牺牲了性能（用 String Map 存协议参）。我们必须反其道而行之，使用 **Union + Struct** 存储协议参，牺牲一点点通用性（需要预定义支持的协议结构），换取**嵌入式所需的极致内存和 CPU 效率**。

# 第三章：自动发现与动态配置 (Discovery & Provisioning)

本章重点：如何设计一套机制，让 SDK 能够自动感知物理连接的变化（如 USB 插入），扫描总线上的设备（如 Modbus 寻址），并自动在系统中生成设备实例。

## 1. EdgeX 源码深度剖析

### 1.1 `ProvisionWatcher` (守望者机制)
在 `src/c/discovery.c` 中，EdgeX 引入了 **ProvisionWatcher** 的概念。
*   **作用**：它是一组“过滤规则”。即使驱动扫描到了设备，如果它不符合 Watcher 的规则（比如 MAC 地址不在白名单，或者 Profile 不匹配），也不会被接入。
*   **流程**：
    1.  `Scheduler` 触发 Discovery 事件。
    2.  `Driver` 执行扫描（如扫描 IP 段），返回一堆原始信息（Raw Metadata）。
    3.  `SDK` 遍历所有 Watchers，匹配这些信息。
    4.  匹配成功 $\rightarrow$ 调用 Metadata 服务创建 Device 实例。

### 1.2 局限性分析 (C语言视角)
*   **纯周期性轮询**：EdgeX 的发现主要依赖定时器。但在 Linux 边缘设备上，我们其实可以利用 **内核事件 (Netlink/Udev)** 来实现更实时的发现。
*   **协议依赖**：EdgeX 强依赖 REST API 来注册设备，这在断网或系统启动初期（HTTP 服务未就绪）时会失效。

### 3.1 物理层发现：监听 `libudev` (Hotplug)

这是 Linux 赋予我们的超能力。当用户插入一个 USB 串口设备时，我们不需要轮询 `/dev/ttyUSB*`，内核会通知我们。

**文件:** `src/core/hotplug_linux.c`

```c
#include <libudev.h>
#include <uv.h>

// Udev 监控上下文
typedef struct {
    struct udev *udev;
    struct udev_monitor *mon;
    uv_poll_t poll_handle;
    EdgeContext *ctx;
} HotplugCtx;

// 当有硬件插拔时触发
static void _on_udev_event(uv_poll_t *handle, int status, int events) {
    HotplugCtx *hc = (HotplugCtx*)handle->data;
    struct udev_device *dev = udev_monitor_receive_device(hc->mon);
    
    if (dev) {
        const char *action = udev_device_get_action(dev);
        const char *node = udev_device_get_devnode(dev);
        const char *subsys = udev_device_get_subsystem(dev);

        if (strcmp(action, "add") == 0 && strcmp(subsys, "tty") == 0) {
            zlog_info(hc->ctx->logger, "New Serial Device Detected: %s", node);
            
            // 触发 SDK 的自动扫描任务
            // task_submit(scan_new_serial_port, strdup(node));
        }
        
        udev_device_unref(dev);
    }
}

int hotplug_init(EdgeContext *ctx) {
    HotplugCtx *hc = calloc(1, sizeof(HotplugCtx));
    hc->ctx = ctx;
    hc->udev = udev_new();
    hc->mon = udev_monitor_new_from_netlink(hc->udev, "udev");
    
    // 只监听 tty (串口) 和 net (网卡) 子系统
    udev_monitor_filter_add_match_subsystem_devtype(hc->mon, "tty", NULL);
    udev_monitor_filter_add_match_subsystem_devtype(hc->mon, "net", NULL);
    udev_monitor_enable_receiving(hc->mon);
    
    // 获取 fd 并挂载到 libuv
    int fd = udev_monitor_get_fd(hc->mon);
    uv_poll_init(ctx->loop, &hc->poll_handle, fd);
    hc->poll_handle.data = hc;
    uv_poll_start(&hc->poll_handle, UV_READABLE, _on_udev_event);
    
    return 0;
}
```

```c
iot_data_t* modbus_scan(void *impl, const char *port, scan_config_t *cfg) {
    iot_data_t *found_list = iot_data_alloc_list();
    modbus_t *ctx = modbus_new_rtu(port, 9600, 'N', 8, 1);
    
    // 极其重要的设置：快速超时
    // 扫描时不能等 1秒，通常 50ms 没回就是没有
    modbus_set_response_timeout(ctx, 0, 50000); 
    modbus_connect(ctx);

    for (int id = cfg->start_addr; id <= cfg->end_addr; id++) {
        modbus_set_slave(ctx, id);
        uint16_t reg_val;
        
        // 尝试读取 0x0000 保持寄存器，作为"Ping"
        if (modbus_read_registers(ctx, 0, 1, &reg_val) != -1) {
            // 发现设备！
            printf("Found Modbus Device at ID: %d\n", id);
            
            iot_data_t *dev = iot_data_alloc_map();
            iot_data_string_map_add(dev, "Interface", port);
            iot_data_string_map_add_int(dev, "SlaveID", id);
            iot_data_string_map_add_int(dev, "PingReg", reg_val); // 指纹
            
            iot_data_list_add(found_list, dev);
        }
    }
    
    modbus_close(ctx);
    modbus_free(ctx);
    return found_list;
}
```

### 3.3 自动发放 (Provisioning)：从指纹到实例

当驱动扫到一个设备后，SDK 需要决定**它是谁**（匹配 Profile），并**入库**。

**文件:** `src/core/provision.c`

```c
// 设备指纹匹配逻辑
// 这里的 logic 类似于 EdgeX 的 ProvisionWatcher
static const char* _match_profile(EdgeContext *ctx, iot_data_t *fingerprint) {
    int ping_val = iot_data_string_map_get_int(fingerprint, "PingReg");
    
    // 简单硬编码逻辑，实际应查询 SQLite 中的规则表
    // 规则表: CREATE TABLE provisioning_rules (match_expr TEXT, profile_name TEXT);
    // 比如 match_expr: "PingReg == 12345" -> "Meter_Type_A"
    
    if (ping_val == 1001) return "Huawei_Inverter_V3";
    if (ping_val == 2002) return "Chint_Meter_DTSU666";
    
    return NULL; // 未知设备
}

void edge_provision_devices(EdgeContext *ctx, iot_data_t *scanned_list) {
    iot_data_list_iter_t iter;
    iot_data_list_iter(scanned_list, &iter);
    
    while (iot_data_list_iter_next(&iter)) {
        iot_data_t *fp = iot_data_list_iter_value(&iter);
        
        // 1. 匹配 Profile
        const char *profile = _match_profile(ctx, fp);
        if (!profile) {
            zlog_warn(ctx->logger, "Unknown device found, skipping.");
            continue;
        }
        
        // 2. 生成设备名
        int slave_id = iot_data_string_map_get_int(fp, "SlaveID");
        char dev_name[64];
        snprintf(dev_name, 64, "%s_%d", profile, slave_id);
        
        // 3. 检查是否已存在 (查 DB)
        if (db_device_exists(ctx, dev_name)) continue;
        
        // 4. 入库 (SQLite)
        // 这会触发 Config Watcher，导致服务重新加载设备列表
        db_create_device(ctx, dev_name, profile, fp);
        zlog_info(ctx->logger, "Auto-provisioned device: %s", dev_name);
    }
}
```

# 第四章：北向导出与离线缓存 (Export & Store-and-Forward)

本章重点：如何设计一个高效的导出引擎，既能支持多种上云协议（MQTT, HTTPS, IEC104），又能保证在断网时数据写入磁盘，联网后自动补传，且不阻塞实时采集业务。

## 1. EdgeX 源码深度剖析

### 1.1 `App Service Configurable` (流水线模式)
EdgeX 的导出逻辑位于 `app-service-configurable` 中。它采用 **Pipeline (流水线)** 设计模式：
*   **Trigger**: 消息总线收到数据。
*   **Functions**: 链式处理。`Filter` (过滤) -> `Transform` (转 JSON/XML) -> `Compress` (压缩) -> `Encrypt` (加密) -> `Export` (发送)。
*   **Store-and-Forward**: EdgeX 使用 **Redis** 或 **内存队列** 作为重试缓冲区。

### 1.2 局限性分析 (C语言视角)
*   **Redis 依赖**: 对于只有 256MB 内存的终端，跑一个 Redis 专门做队列太奢侈。
*   **HTTP 依赖**: EdgeX 的导出服务倾向于 HTTP/REST，但在弱网环境下，**MQTT (长连接)** 和 **IEC 104 (TCP)** 才是王道。
*   **实时性**: Go 语言的 GC 和多层 Channel 传递在高频（10ms）场景下会有抖动。

## 2. 吸收与改良：针对 EdgeOS 的优化设计

我们保留 EdgeX 的 **Pipeline** 思想，但将其实现极致轻量化。

| 特性 | EdgeX (原版) | EdgeOS SDK (改良版) | 核心理由 |
| :--- | :--- | :--- | :--- |
| **缓存介质** | Redis / Memory | **SQLite (WAL Mode)** | 掉电不丢数据，支持 GB 级缓存 |
| **发送策略** | 失败后重试 | **优先直发，失败入库，空闲补发** | 减少正常情况下的 Flash 写入寿命损耗 |
| **打包策略** | 单点发送 | **Batching (聚合发送)** | 减少 4G 流量开销和协议头占比 |
| **多云支持** | 多服务实例 | **多通道 (Channel) 设计** | 一个进程内支持同时发给阿里云和国网主站 |

### 3.3 核心策略：智能补传状态机

我们不能简单的“一通乱发”。需要一个状态机来管理**实时流**和**补传流**的竞争。

**文件:** `src/core/export_manager.c`

```c
// 数据发送主逻辑
void export_send_data(export_channel_t *ch, DataPoint *dp) {
    // 1. 序列化数据 (转 JSON 或 二进制)
    // 这里的 buffer 来自内存池
    net_buf_t *payload = serialize_to_json(dp); 

    // 2. 检查网络状态
    if (ch->is_online) {
        // 尝试直发
        int ret = ch->ops->send(ch, payload->data, payload->len);
        if (ret == 0) {
            // 发送成功，直接释放内存，不走磁盘
            net_buf_free(payload);
            return;
        } else {
            // 发送失败 (即使 marked online)，转入缓存
            zlog_warn(ch->ctx->logger, "Send failed, switching to offline mode.");
            ch->is_online = 0;
            // 启动补传定时器
            uv_timer_start(&ch->retry_timer, _on_retry_tick, 5000, 5000);
        }
    }

    // 3. 写入缓存 (Store)
    if (ch->enable_cache) {
        queue_push(ch->ctx, ch->name, "data_topic", payload->data, payload->len);
    }
    net_buf_free(payload);
}

// 补传定时器回调 (Drain)
static void _on_retry_tick(uv_timer_t *handle) {
    export_channel_t *ch = (export_channel_t*)handle->data;
    
    // 1. 尝试 Ping 一下或者发一个 Heartbeat
    // 如果物理链路没通，直接返回，省得去读数据库
    
    // 2. 从数据库取一批
    QueueItem *items;
    int count = queue_pop_batch(ch->ctx, ch->name, 50, &items);
    
    if (count == 0) {
        // 队列空了，恢复实时模式，停止定时器
        ch->is_online = 1;
        uv_timer_stop(&ch->retry_timer);
        return;
    }

    // 3. 批量发送
    for (int i=0; i<count; i++) {
        if (ch->ops->send(ch, items[i].data, items[i].len) == 0) {
            // 发送成功，标记删除 ID
            mark_for_delete(items[i].id);
        } else {
            // 只要有一条失败，认为网络又不通了，停止本轮补传
            return; 
        }
    }
    
    // 4. 提交删除事务
    queue_delete_batch(ch->ctx, deleted_ids, count);
}
```

### 3.4 流量优化：聚合发送 (Batching)

对于 MQTT，每秒发 100 个 50 字节的包是低效的（Header 开销大）。我们需要 **Nagle 算法** 风格的聚合。

**实现思路**：
1.  SDK 内部维护一个 `net_buf_t *current_batch`。
2.  收到数据点，追加到 `current_batch` 尾部（JSON Array Append）。
3.  **触发发送条件**：
    *   buffer 大小超过阈值 (如 4KB)。
    *   或者，距离上一条数据超过 100ms (Time-out)。

```c
void export_batch_add(export_channel_t *ch, DataPoint *dp) {
    // 追加到缓存
    json_array_append(ch->batch_buf, dp);
    
    if (ch->batch_buf->len > 4096) {
        export_flush(ch); // 立即发送
        return;
    }
    
    // 重置延迟发送定时器
    // 如果 100ms 内没有新数据，就发送当前 buffer
    uv_timer_again(&ch->flush_timer);
}
```

# 第五章：安全子系统 (Security Subsystem)

本章重点：如何在 C 语言 SDK 中集成**硬件安全芯片 (SE/HSM)**，实现基于国密算法（SM2/SM3/SM4）的密钥管理、数据加密、以及对上层微应用的签名校验。

## 1. EdgeX 源码深度剖析

### 1.1 `Security Service` (基于 Vault)
EdgeX 使用 HashiCorp 的 **Vault** 作为密钥存储（Secret Store），使用 **Kong** 作为 API 网关。
*   **流程**：微服务启动时，通过 HTTP 请求 Vault 获取数据库密码或 MQTT 证书。
*   **优点**：企业级安全，支持密钥轮转、动态策略。

### 1.2 局限性分析 (嵌入式视角)
*   **资源噩梦**：Vault 是用 Go 写的，Kong 是基于 Nginx + Lua 的。这两个组件跑起来就要消耗几百 MB 内存，这在嵌入式终端上是不现实的。
*   **软件安全 vs 硬件安全**：EdgeX 的安全是基于软件的（Master Key 存在磁盘上）。而电网标准强制要求**私钥不出安全芯片**。

---

## 2. 吸收与改良：针对 EdgeOS 的硬核设计

我们抛弃 Vault，直接对接 **板载 SE 芯片**（如紫光同芯、华大电子）。

| 特性 | EdgeX (原版) | EdgeOS SDK (改良版) | 核心理由 |
| :--- | :--- | :--- | :--- |
| **信任根 (RoT)** | 软件文件 | **SE 安全芯片** | 物理层面的防篡改，私钥无法导出 |
| **算法标准** | RSA/AES/SHA | **SM2/SM3/SM4** | 符合国网/南网 2025 标准 |
| **密钥存储** | Vault (DB) | **Key Wrapping (密钥包裹)** | 业务密钥被 SE 的根密钥加密后存文件 |
| **应用校验** | 无 / 容器签名 | **ELF 签名校验** | 在 `dlopen` 加载插件前校验数字签名 |

---

## 3. 新设计文档：Security Engine

### 3.1 硬件抽象层：SE Driver HAL

不同厂家的 SE 芯片接口（ISO7816 APDU 指令）略有不同，我们需要一层 HAL。

**文件:** `include/hal/se_driver.h`

```c
#ifndef SE_DRIVER_H
#define SE_DRIVER_H

#include <stdint.h>

// 密钥类型索引
typedef enum {
    KEY_ID_DEVICE_AUTH  = 1, // 设备身份私钥 (SM2)
    KEY_ID_STORAGE_ROOT = 2, // 存储加密根密钥 (SM4)
    KEY_ID_UPDATE_PUB   = 3  // OTA/APP 验签公钥 (SM2)
} KeyID;

typedef struct {
    // 1. 初始化 SE (打开 I2C/SPI 设备)
    int (*init)(void);
    
    // 2. 获取随机数 (真随机数发生器 TRNG)
    int (*get_random)(uint8_t *buf, size_t len);
    
    // 3. 签名 (使用内部私钥，数据进，签名出)
    // 核心：私钥永远不离开芯片
    int (*sign)(KeyID key_id, const uint8_t *hash, size_t hash_len, uint8_t *sig, size_t *sig_len);
    
    // 4. 验签 (使用内部/外部公钥)
    int (*verify)(KeyID key_id, const uint8_t *hash, size_t len, const uint8_t *sig, size_t sig_len);
    
    // 5. 对称加解密 (SM4-ECB/CBC)
    int (*encrypt)(KeyID key_id, const uint8_t *in, size_t len, uint8_t *out);
    int (*decrypt)(KeyID key_id, const uint8_t *in, size_t len, uint8_t *out);
} se_driver_t;

// 获取全局单例
se_driver_t* se_get_instance(void);

#endif
```

### 3.2 核心服务：OpenSSL Engine 集成

这是最巧妙的一步。
你的 MQTT 库 (libmosquitto) 或 HTTPS 库 (libcurl) 通常支持 OpenSSL。如果我们自己写一套加解密 API，这些第三方库是用不上的。
**解决方案**：编写一个 **OpenSSL Engine** 插件，拦截 OpenSSL 的算法调用，转发给 SE 芯片。

**文件:** `src/security/engine_sm.c` (示意)

```c
/* 
 * 这是一个 OpenSSL Engine 的钩子函数。
 * 当上层应用调用 RSA_sign 或 EVP_PKEY_sign 时，会走到这里。
 */
static int se_sm2_sign(EVP_PKEY_CTX *ctx, unsigned char *sig, size_t *siglen,
                       const unsigned char *tbs, size_t tbslen) {
    // 1. 获取 SDK 的 SE 驱动实例
    se_driver_t *se = se_get_instance();
    
    // 2. 调用硬件签名
    // 注意：OpenSSL 通常处理的是 Hash 后的数据
    int ret = se->sign(KEY_ID_DEVICE_AUTH, tbs, tbslen, sig, siglen);
    
    return (ret == 0) ? 1 : 0;
}

// 注册 Engine
void edge_security_init_engine() {
    ENGINE *e = ENGINE_new();
    ENGINE_set_id(e, "se_chip_sm");
    ENGINE_set_name(e, "Hardware SE SM2/SM3/SM4 Engine");
    
    // 绑定算法钩子
    ENGINE_set_pkey_meths(e, se_sm2_pkey_methods);
    ENGINE_set_ciphers(e, se_sm4_ciphers);
    
    ENGINE_add(e);
    ENGINE_set_default(e, ENGINE_METHOD_ALL); // 设为默认
}
```

**效果**：一旦初始化了这个 Engine，你的 `libmosquitto` 在建立 TLS 连接时，会自动调用 SE 芯片进行握手，**你一行 MQTT 代码都不用改**。

### 3.3 数据隐私：密钥包裹 (Key Wrapping)

我们之前设计的 **SQLite 存储** 需要加密。但数据库密码存在哪？
**绝对不能写在代码里！**

**设计方案**：
1.  设备出厂时，SE 芯片内生成一个 `Storage_Root_Key` (SM4)。
2.  SDK 首次运行时，随机生成一个 `DB_Password`。
3.  调用 SE 芯片，用 `Storage_Root_Key` 对 `DB_Password` 进行加密，得到 `Wrapped_Password`。
4.  将 `Wrapped_Password` 存在文件系统 (`/etc/edge/db.secret`)。

**启动流程 (`src/core/secure_storage.c`)**：

```c
char* edge_sec_get_db_password(EdgeContext *ctx) {
    // 1. 从文件读取密文
    uint8_t wrapped[32];
    read_file("/etc/edge/db.secret", wrapped, 32);
    
    // 2. 送入 SE 解密
    uint8_t plain[32];
    se_driver_t *se = se_get_instance();
    se->decrypt(KEY_ID_STORAGE_ROOT, wrapped, 32, plain);
    
    // 3. 返回明文给 SQLite (只在内存中短暂存在)
    return strdup((char*)plain);
}

// 初始化 SQLite 时调用
void db_secure_open(EdgeContext *ctx) {
    char *pwd = edge_sec_get_db_password(ctx);
    sqlite3_open_v2(path, &db, ...);
    // 使用 SQLCipher 扩展 (如果是国密版则是 SQLCipher-SM4)
    sqlite3_key(db, pwd, strlen(pwd));
    
    // 立即擦除内存中的密码
    memset(pwd, 0, strlen(pwd));
    free(pwd);
}
```

### 3.4 应用沙箱：签名校验 (App Signing)

我们在第七批次提到过“微应用容器化”。为了防止黑客替换 `.so` 文件植入木马，必须在加载前验签。

**文件:** `src/core/plugin_loader_sec.c`

```c
// 加载插件的安全封装
void* edge_dlopen_secure(const char *path) {
    // 1. 计算 .so 文件的 SM3 哈希值
    uint8_t hash[32];
    calc_file_sm3(path, hash);
    
    // 2. 读取签名文件 (e.g., app.so.sig)
    char sig_path[256];
    snprintf(sig_path, sizeof(sig_path), "%s.sig", path);
    uint8_t sig[64];
    read_file(sig_path, sig, 64);
    
    // 3. 调用 SE 验签 (使用内置的 OTA/APP 更新公钥)
    se_driver_t *se = se_get_instance();
    int ret = se->verify(KEY_ID_UPDATE_PUB, hash, 32, sig, 64);
    
    if (ret != 0) {
        printf("[Security] FATAL: Signature verification failed for %s\n", path);
        return NULL; // 拒绝加载
    }
    
    // 4. 验签通过，放行
    return dlopen(path, RTLD_NOW);
}
```

# 第六章：微应用容器与资源调度 (Micro-App Container)

本章重点：如何在 Linux 环境下，不依赖 Docker（太重），构建一套**轻量级应用容器**。我们将利用 Linux 内核原生的 **Cgroups** 进行资源限制，设计一套标准的 **C API** 供第三方开发者使用。

## 1. EdgeX 源码深度剖析

### 1.1 `App Functions SDK` (微服务架构)
EdgeX 的应用层是基于 **Microservices** 的。
*   **部署**：每个 App 是一个独立的 Docker 容器。
*   **通信**：通过 HTTP/REST 或 MQTT 触发。
*   **隔离**：Docker Engine 负责资源隔离。

### 1.2 局限性分析 (嵌入式视角)
*   **资源开销**：Docker Daemon 本身占用内存，且每个容器启动都需要独立的 Filesystem 层，对于 256MB/512MB 的终端来说，跑 5 个 Docker 容器基本就 OOM（内存溢出）了。
*   **启动速度**：容器启动通常需要秒级，而在断电重启场景下，保护类业务（如过流保护 App）需要毫秒级启动。

---

## 2. 吸收与改良：针对 EdgeOS 的原生容器设计

我们不造 Docker，我们直接使用 Linux 内核原语构建一个**“进程沙箱”**。

| 特性 | EdgeX (Docker) | EdgeOS SDK (Process Container) | 核心理由 |
| :--- | :--- | :--- | :--- |
| **运行实体** | Docker Container | **Native Process (ELF)** | 无虚拟化开销，启动速度快 (<10ms) |
| **资源限制** | Docker CLI | **Cgroups (v1/v2)** | 精确限制每个 App 的 CPU % 和 RAM 限额 |
| **生命周期** | Docker Daemon | **App Manager (SDK 内置)** | 由主进程直接 fork/exec，失去响应立即重启 |
| **API 暴露** | REST / MessageBus | **SDK Shared Library (.so)** | 封装 IPC 细节，提供函数级 API |

---

## 3. 新设计文档：App Runtime Engine

### 3.1 核心组件：App Manager (应用管家)

这是 SDK 的一个子系统，负责管理所有微应用的生老病死。

**设计逻辑**：
1.  **安装**：解压 App 包（含 ELF 二进制、签名、`manifest.json`）。
2.  **安全检查**：调用 Security 子系统验签。
3.  **启动**：`fork()` -> 配置 Cgroups -> `exec()`。
4.  **监控**：监听 `SIGCHLD` 信号，如果 App 异常退出，按策略重启。

**文件:** `src/apps/app_manager.c`

```c
#include <sys/wait.h>
#include <unistd.h>
#include "cgroup_utils.h"

typedef struct {
    char name[32];
    char exec_path[256];
    int pid;
    int memory_limit_mb;
    int cpu_shares;
    int restart_count;
} MicroApp;

// 启动一个微应用
int app_start(EdgeContext *ctx, MicroApp *app) {
    pid_t pid = fork();
    
    if (pid < 0) {
        return -1;
    } else if (pid == 0) {
        // --- 子进程上下文 ---
        
        // 1. 自我加入 Cgroups (资源限制)
        // 注意：这里需要父进程提前创建好 cgroup 节点，或者赋予子进程权限
        // 更好的做法是父进程在 fork 后，exec 前把子进程 PID 写入 cgroup
        
        // 2. 降低权限 (Drop Privileges)
        // 从 root 切换到普通用户 edge_app
        setuid(1001); 
        
        // 3. 设置环境变量，传入 IPC 地址
        setenv("EDGE_IPC_ADDR", "ipc:///tmp/edge_bus.sock", 1);
        
        // 4. 执行业务逻辑
        execl(app->exec_path, app->name, NULL);
        
        // 如果执行到这，说明 exec 失败
        exit(1);
    } else {
        // --- 父进程上下文 ---
        app->pid = pid;
        
        // 1. 将子进程加入 Cgroup 限制资源
        cgroup_limit_memory(app->name, app->memory_limit_mb);
        cgroup_limit_cpu(app->name, app->cpu_shares, pid);
        
        zlog_info(ctx->logger, "App %s started, PID=%d", app->name, pid);
    }
    return 0;
}

// 僵尸进程回收与重启策略
void app_monitor_loop(EdgeContext *ctx) {
    int status;
    pid_t pid = waitpid(-1, &status, WNOHANG);
    
    if (pid > 0) {
        MicroApp *app = find_app_by_pid(pid);
        if (app) {
            zlog_warn(ctx->logger, "App %s crashed!", app->name);
            // 简单的指数退避重启策略
            if (app->restart_count < 5) {
                app->restart_count++;
                app_start(ctx, app);
            }
        }
    }
}
```

## 2. 质量门禁：CI/CD 流水线

代码提交后，不能只靠人眼 Review。必须由机器进行“三维扫描”。

### 2.1 静态分析 (Static Analysis)
在编译前，扫描逻辑漏洞。
*   **工具**：`cppcheck`
*   **命令**：`cppcheck --enable=all --inconclusive --error-exitcode=1 src/`
*   **检测点**：未初始化的变量、缓冲区溢出风险、死代码。

### 2.2 动态分析 (Dynamic Analysis)
在单元测试运行时，检测内存问题。
*   **工具**：`AddressSanitizer (ASan)` + `LeakSanitizer`。
*   **检测点**：
    *   Use-after-free (释放后使用，C 语言大忌)
    *   Memory Leaks (内存泄漏)
    *   Heap Buffer Overflow (堆溢出)

### 2.3 自动化测试脚本 (`.gitlab-ci.yml` 参考)

```yaml
stages:
  - lint
  - build
  - test

static_check:
  stage: lint
  script:
    - cppcheck --enable=all --error-exitcode=1 src/

build_debug:
  stage: build
  script:
    - mkdir build && cd build
    - cmake -DCMAKE_BUILD_TYPE=Debug ..
    - make -j4
  artifacts:
    paths:
      - build/bin/run_tests

unit_test_asan:
  stage: test
  dependencies:
    - build_debug
  script:
    # 运行编译出的测试程序，如果 ASan 发现内存错误，进程会 crash，导致 CI 失败
    - ./build/bin/run_tests
```

## 3. 产测工具：Factory Mode

SG-EL2025 主板生产出来后，需要在流水线上快速判断良品/不良品。
**SDK 必须提供一个独立的 `factory_test` 程序**，不依赖云端，不依赖复杂配置，开机即跑。

### 3.1 产测流程设计

1.  **LED 交互**：红灯闪烁（测试中） -> 绿灯常亮（通过） / 红灯常亮（失败）。
2.  **外设遍历**：
    *   **SE 芯片**：尝试签名/验签（验证 I2C/SPI 通路）。
    *   **4G 模块**：发送 AT 指令查询 IMEI/IMSI（验证 UART）。
    *   **RS485**：短接 A/B，发送数据看是否回显（Loopback Test）。
    *   **存储**：写入 10MB 文件并读取校验 MD5（验证 Flash 坏块）。

### 3.2 代码实现 (`tools/factory_test/main.c`)

```c
#include "edge_hal.h"

typedef struct {
    const char *name;
    int (*test_func)(void);
} TestItem;

int test_se_chip() {
    // 调用 HAL 层接口尝试获取随机数
    uint8_t buf[16];
    if (hal_se_get_random(buf, 16) == 0) return 0; // Pass
    return -1; // Fail
}

int test_storage() {
    // 写入测试文件
    FILE *fp = fopen("/data/test.tmp", "w");
    if (!fp) return -1;
    // ... write & read & verify ...
    return 0;
}

TestItem items[] = {
    {"SE_CHIP", test_se_chip},
    {"STORAGE", test_storage},
    {"RS485_1", test_rs485_1},
    {NULL, NULL}
};

int main() {
    printf("=== FACTORY TEST MODE ===\n");
    hal_led_set(LED_RED, LED_BLINK);
    
    int all_pass = 1;
    for (int i=0; items[i].name; i++) {
        printf("Testing %s ... ", items[i].name);
        if (items[i].test_func() == 0) {
            printf("[PASS]\n");
        } else {
            printf("[FAIL]\n");
            all_pass = 0;
        }
    }
    
    if (all_pass) {
        hal_led_set(LED_GREEN, LED_ON);
        printf("RESULT: PASS\n");
    } else {
        hal_led_set(LED_RED, LED_ON);
        printf("RESULT: FAIL\n");
    }
    return all_pass ? 0 : 1;
}
```

## 4. 现场运维：Edge CLI 工具

当设备在现场出问题时，运维人员通过 SSH 登录，需要一个类似 `docker` 或 `systemctl` 的工具来查看 SDK 内部状态，而不是去 grep 日志。

### 4.1 架构设计

*   **Server 端 (SDK)**：创建一个 Unix Domain Socket (`/tmp/edge_cli.sock`)，监听命令。
*   **Client 端 (edge-cli)**：发送文本命令，接收 JSON 响应并格式化打印。

### 4.2 核心命令集

| 命令 | 描述 | 内部实现逻辑 |
| :--- | :--- | :--- |
| `edge-cli list` | 列出所有微应用及状态 | 遍历 AppManager 链表，返回 PID、CPU%、Uptime |
| `edge-cli driver ls` | 列出加载的驱动 | 遍历 PluginManager，返回 .so 列表和协议统计 |
| `edge-cli data get <tag>` | 读取实时数据 | 查询 Shared Memory (shm_ring) |
| `edge-cli log level <lvl>` | 动态调整日志级别 | 修改 zlog 配置，无需重启 |
