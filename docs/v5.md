# 🚀 EdgeOS SDK 架构设计白皮书 (v1.0)

**目标**：构建一套基于 C 语言的、面向对象的、模块化的工业级边缘计算框架。
**核心哲学**：逻辑借鉴 EdgeX (解耦/配置驱动)，实现对标 Linux Kernel (零拷贝/硬实时)。

## 第一部分：顶层架构与设计哲学 (Architecture & Philosophy)

### 1.1 总体架构图 (The Big Picture)

我们将系统划分为四层。请指导团队严格遵守**层级依赖原则**：上层可以调用下层，下层严禁反向依赖上层（只能通过回调）。

```text
+-----------------------------------------------------------------------------------+
|                          Layer 4: 业务应用层 (Business Apps)                      |
| [ HEMS Logic ]  [ IEMS Strategy ]  [ EVSE Billing ]  [ DCU Metering ]  [ SG-APP ] |
| (动态库/微应用)   (MPC/PID算法)      (状态机FSM)       (补抄逻辑)        (容器化)   |
+-----------------------------------------------------------------------------------+
                                      | (API / IPC)
+-----------------------------------------------------------------------------------+
|                          Layer 3: 设备服务框架 (Device Framework)                 |
|               *** 深度借鉴 EdgeX Device SDK 的核心层 ***                          |
| [ Service Context ]  [ Device Profile ]  [ Auto Discovery ]  [ Admin State ]      |
| (生命周期管理)       (元数据映射)        (Udev/Scan)         (运维状态机)         |
+-----------------------------------------------------------------------------------+
                                      | (Function Calls)
+-----------------------------------------------------------------------------------+
|                          Layer 2: 核心运行时 (Core Runtime)                       |
| [ Scheduler V3 ]     [ Data Pipeline ]   [ Secure Bus ]      [ Async Storage ]    |
| (TimerFD/MinHeap)    (流式计算/DSP)      (MQTT/SHM)          (SQLite WAL)         |
+-----------------------------------------------------------------------------------+
                                      | (HAL Interface)
+-----------------------------------------------------------------------------------+
|                          Layer 1: 硬件抽象与驱动 (HAL & Drivers)                  |
| [ libuv (Loop) ]     [ net_buf (Mem) ]   [ dma-buf (ZeroCopy)]  [ SE Driver ]     |
+-----------------------------------------------------------------------------------+
```

### 1.2 核心设计模式 (Design Patterns)

指导团队时，必须强调以下三种模式：

1.  **C 语言面向对象 (Object-Oriented C)**
    *   **规则**：严禁使用全局变量。所有操作必须围绕 `Context` (上下文) 进行。
    *   **实现**：使用结构体模拟 Class，使用函数指针模拟 Virtual Function（多态）。
    *   **目的**：支持多实例，支持单元测试 Mock。

2.  **控制反转 (IoC - Inversion of Control)**
    *   **借鉴 EdgeX**：驱动开发者**不写 main 函数**，只实现 `init`, `read`, `write` 接口。SDK 接管主循环。
    *   **目的**：让业务开发只需关注“读写寄存器”，而不用管“怎么连 MQTT”、“怎么存数据库”。

3.  **元数据驱动 (Metadata Driven)**
    *   **借鉴 EdgeX**：代码中严禁硬编码寄存器地址（如 `0x0001`）。
    *   **实现**：所有物理信息必须在 **Device Profile (YAML/JSON)** 中定义，运行时加载。

## 第二部分：核心运行时设计 (Core Runtime Specification)

这是 SDK 的发动机。涵盖了**内存、调度、总线**。

### 2.1 上下文对象 (`edge_context_t`)

这是所有服务的基石。

```c
typedef struct edge_context_s {
    // 1. 基础设施
    uv_loop_t *loop;           // 事件循环核心
    void *mem_pool;            // Slab 内存池 (net_buf)

    // 2. 核心服务句柄 (单例)
    void *scheduler;           // 调度服务
    void *storage;             // 存储服务
    void *bus;                 // 消息总线
    void *security;            // 安全服务 (SE)

    // 3. 配置
    edge_config_t *sys_config; // 系统级配置

    // 4. 扩展点
    void *user_data;           // 预留给上层的指针
} edge_context_t;
```

### 2.2 内存管理：`net_buf` + `dma-buf` 双轨制

针对 **嵌入式明珠**（DSP/AI）的需求，必须设计两条内存通道：

1.  **控制通道 (Control Plane)** -> 使用 **`net_buf`**
    *   **场景**：Modbus 报文、MQTT JSON、配置参数。
    *   **实现**：移植 Zephyr 的 `net_buf`，支持 `ref` 引用计数和 `headroom` 操作。
    *   **要求**：禁止在通信热路径使用 `malloc`。

2.  **数据通道 (Data Plane)** -> 使用 **`dma-buf`**
    *   **场景**：SG-EL2025 的 AC 波形、NILM 的特征图、视频流。
    *   **实现**：封装 `/dev/dma_heap`。FPGA/ADC 直接写入物理内存，DSP/NPU 直接读取。
    *   **API**：`hw_buf_alloc()`, `hw_buf_map()`, `hw_buf_sync_cpu()`.

### 2.3 调度器：Scheduler V3 (抗时钟跳变)

针对 IEMS/DCU 的**定时任务**和**补抄逻辑**。

*   **数据结构**：**Min-Heap (最小堆)**，O(1) 获取最近任务。
*   **驱动源**：Linux **`timerfd`** + `CLOCK_REALTIME` + `TFD_TIMER_CANCEL_ON_SET`。
*   **功能**：
    *   支持 Cron 表达式 (`0 0 12 * * *`)。
    *   **关键特性**：当 NTP 同步导致时间跳变时，内核立刻唤醒 SDK，SDK 瞬间重排任务堆，**零延迟响应**。

## 第三部分：设备服务框架 (Device Service Framework)

**这是对 EdgeX Device SDK 的深度复刻与嵌入式改良。**

### 3.1 核心结构体 (`edge_service_t`)

这个结构体对应 EdgeX 的 `devsdk_service_t`，是驱动开发的入口。

```c
typedef struct edge_service_s {
    // [元数据]
    char *name;

    // [回调契约] - 驱动必须实现的接口 (借鉴 EdgeX userfns)
    struct {
        bool (*init)(void *impl, struct edge_service_s *svc);
        bool (*read)(void *impl, const char *dev, const char *res, edge_reading_t *out);
        bool (*write)(void *impl, const char *dev, const char *res, const edge_value_t *val);
        void (*stop)(void *impl);
        // 新增：自动发现回调
        void (*discover)(void *impl, const scan_config_t *cfg);
    } driver;

    void *driver_impl_data; // 驱动私有数据

    // [设备管理] - 对应 EdgeX Device/Profile
    edge_device_map_t *devices;  // 内存中的设备列表
    edge_profile_map_t *profiles;// 加载的 Profile 缓存

    // [状态机]
    admin_state_t admin_state;   // LOCKED/UNLOCKED (运维锁定)

    // [运行时]
    edge_context_t *ctx;         // 指向核心运行时
} edge_service_t;
```

### 3.2 动态配置与 Profile 引擎

*   **Profile 加载**：
    *   EdgeX 使用 YAML，我们使用 **SQLite** 预编译。
    *   在 PC 端提供工具，将 YAML 转换为 SQL 脚本或二进制 Profile，下载到终端。
    *   **运行时**：`read_resource("Voltage")` -> 查 Hash 表 -> 找到 `Modbus:4001, Float32` -> 调用驱动 `read`。

*   **配置热更新 (Inotify)**：
    *   监控配置文件变化。当配置更新（如轮询间隔改变），自动调整 Scheduler 中的 Timer，无需重启进程。

### 3.3 自动发现 (Discovery) 流程

1.  **触发**：
    *   **物理触发**：`udev` 监听到 `/dev/ttyUSB0` 插入。
    *   **定时触发**：Scheduler 每 10 分钟触发一次。
2.  **执行**：
    *   SDK 调用驱动的 `driver.discover()` 接口。
    *   驱动执行协议扫描（如 Modbus 遍历 SlaveID 1-10）。
3.  **匹配 (Provisioning)**：
    *   SDK 拿到驱动返回的指纹（如 0x00 寄存器值）。
    *   遍历 **ProvisionWatcher** 规则表（EdgeX 概念）。
    *   匹配成功 -> 自动创建 Device 实例 -> 立即开始采集。

## 第四部分：数据管道与高阶算法 (Pipeline & Pearls)

这一部分是将 **“嵌入式明珠”**（FOC/DSP/AI）融入架构的关键。

### 4.1 Data Pipeline 设计

采用 **Chain of Responsibility (责任链)** 模式，处理数据流。

```text
[ Driver ] --> [ Raw Data ]
                    |
            +-------v-------+
            | Pipeline Engine|
            +-------+-------+
                    |
    +---------------v----------------+
    | Stage 1: 变换 (TinyExpr)       |  --> y = kx + b
    +--------------------------------+
    | Stage 2: 过滤 (Deadband)       |  --> |x_new - x_old| > th ?
    +--------------------------------+
    | Stage 3: 高级算法 (DSP/AI)     |  --> FFT / TFLite / MPC
    +--------------------------------+
                    |
            +-------v-------+
            |   Bus Service | --> MQTT / SHM
            +---------------+
```

### 4.2 集成“明珠”算法的策略

1.  **电机/电源控制 (FOC/Digital Power) - IEMS/EVSE**
    *   **策略**：**旁路模式 (Bypass)**。
    *   核心控制回路（10kHz+）直接在 **M核 (MCU)** 或 **FPGA** 中闭环运行。
    *   SDK 只负责：下发目标值（SetPoint），读取状态值（Telemetry）。
    *   **接口**：`shm_ring` (A核 <-> M核)。

2.  **波形分析 (DSP/FFT) - SG-EL2025**
    *   **策略**：**硬件加速模式**。
    *   FPGA 采波形 -> 写入 `dma-buf`。
    *   SDK 收到通知，将 `dma-buf fd` 传给 **NEON 加速库** 或 **NPU**。
    *   Pipeline Stage 只处理分析结果（THD, 谐波含量）。

3.  **AI 预测/策略 (MPC) - IEMS**
    *   **策略**：**异步工作流模式**。
    *   数据进入 Pipeline -> 触发 `uv_queue_work` -> 在线程池中运行 MPC 求解器 (OSQP) -> 结果写回 Bus。

```c
 * Product: IEMS (Industrial Energy Management System)
 * Service: Smart Meter Driver (Modbus/RTU)

#include "edge_sdk.h"  // SDK 核心头文件
#include <stdio.h>
#include <stdlib.h>
#include <signal.h>

// ============================================================================
// Part 1: 驱动实现层 (Driver Implementation)
// 开发者只需要关注业务逻辑，不需要关心 Main Loop、MQTT 或 SQLite
// ============================================================================

// 驱动私有上下文 (Driver Private Context)
typedef struct {
    void *modbus_ctx;      // libmodbus 句柄
    int baud_rate;
    int retry_count;
    // ... 其他私有变量
} my_driver_t;

// 1. 初始化回调 (对应 EdgeX Init)

    edge_log_info(svc, "Initializing Meter Driver for IEMS...");

    // 1. 分配私有内存

    const char *port = edge_conf_get_str(svc->config, "Driver", "Port");
    driver->baud_rate = edge_conf_get_int(svc->config, "Driver", "BaudRate");

    // driver->modbus_ctx = modbus_new_rtu(port, ...);
    // if (modbus_connect(...) == -1) return false;

    edge_log_info(svc, "Driver initialized on %s @ %d bps", port, driver->baud_rate);
    return true;

{
    my_driver_t *driver = (my_driver_t *)impl;

    free(driver);

// 定义契约 (V-Table)
// ----------------------------------------------------------------------------
static edge_callbacks_t my_impl_ops = {
    .init = my_driver_init,
    .read = my_driver_read,
    .write = my_driver_write,
    .stop = my_driver_stop,
    .discover = my_driver_discover,
    .reconfigure = NULL // 可选：支持热更配置

// 这是一个标准的启动模板，90% 的 APP 代码都长这样

    edge_service_t *svc = edge_service_create("iems-meter-service", "1.0.0", product_type);

    if (!svc) {

        return -1;

    // 4. [可选] 加载高级特性 (Add-ons)
    if (product_type == EDGE_PRODUCT_IEMS) {
        // IEMS 需要硬实时调度
        edge_feature_enable(svc, EDGE_FEAT_PREEMPT_RT);
        // IEMS 需要断点续传
        edge_feature_enable(svc, EDGE_FEAT_STORE_FORWARD);
    } else if (product_type == EDGE_PRODUCT_SG_EL2025) {
        // 融合终端需要国密安全
        edge_feature_enable(svc, EDGE_FEAT_SE_SECURITY);
    }

    // 5. 启动服务 (Block Here)
    // SDK 接管一切：
    // - 启动 libuv 事件循环
    // - 启动 Scheduler (TimerFD)
    // - 启动 MQTT/IPC
    // - 只有当收到 SIGINT/SIGTERM 时才会返回
    int ret = edge_service_run(svc);

    // 6. 销毁资源
    edge_service_destroy(svc);

    return ret;
}
```

### 🔍 代码深度解析 (Code Analysis)

这段代码完美诠释了白皮书中的设计理念：

#### 1. 极简的 `main` 函数
主函数里没有 `while(1)`，没有 `sleep`，没有 `malloc`。它只做了一件事：**配置并启动 SDK**。所有的复杂性（事件循环、内存管理、异常捕获）都被封装在 `edge_service_run` 内部。

#### 2. 清晰的依赖注入 (IoC)
注意 `my_driver_init` 函数。SDK 传递了 `edge_service_t *svc` 指针给驱动。驱动想要写日志、读配置，全部通过 `svc` 指针调用 SDK 提供的 API（如 `edge_conf_get_str`）。驱动不需要引用任何全局变量。

#### 3. 抽象的数据交互
在 `my_driver_read` 中，驱动不需要知道数据是要发给 MQTT 还是存入 SQLite。它只需要把读到的寄存器值填入 `edge_reading_t` 结构体。
*   SDK 的 **Pipeline** 会自动接手这个数据，执行 `TinyExpr` 转换（如 `x * 0.1`）。
*   SDK 的 **Bus Service** 会自动分发这个数据（本地 SHM 或 远程 MQTT）。

#### 4. 产品维度的多态 (Polymorphism)
注意 `main` 函数中的 **Feature Toggle**：
```c
if (product_type == EDGE_PRODUCT_IEMS) {
    edge_feature_enable(svc, EDGE_FEAT_PREEMPT_RT);
}
```
这段代码展示了如何用一套代码库支持多个产品。
*   如果是 **HEMS**，这些 Feature 全部关闭，运行时极为轻量。
*   如果是 **SG-EL2025**，开启国密和 DMA 特性，运行时变为高性能模式。

### 第一部分：专家评价 (Evaluation)

#### ✅ 亮点 (Highlights)

1. **分层治理精准**：严守“上层依赖下层，下层回调上层”的原则，这是 C 语言项目避免变成“面条代码”的唯一法宝。
2. **双轨制内存管理**：明确区分 `net_buf` (控制面) 和 `dma-buf` (数据面) 是点睛之笔。这是解决 SG-EL2025（电网分析）和 EVSE（计费）性能矛盾的关键。
3. **抗时钟跳变设计**：提到 `TFD_TIMER_CANCEL_ON_SET` 和 `CLOCK_REALTIME` 的处理，说明你非常懂工业现场（NTP 对时经常导致逻辑混乱）的痛点。
4. **产品形态裁剪**：Kconfig 的引入让一套代码适配从“插座”到“变电站”的全系产品，极具工程智慧。

#### ⚠️ 风险点 (Risks & Gaps)

1. **进程间通信 (IPC) 的具体选型未定**：文档提到了 Bus，但未指明协议。对于 C 语言环境，REST API 太慢，MQTT 内部通信太重。
2. **崩溃恢复机制 (Resilience)**：C 语言最大的弊端是内存错误导致 Crash。架构中缺乏“看门狗”和“崩溃现场保留”的设计。
3. **硬实时的边界**：虽然提到了 Preempt-RT，但用户态（User Space）的调度抖动依然存在。需要明确 RT 线程的 CPU 亲和性与优先级策略。
4. **OTA 与分区策略**：长期演进离不开升级，文档未涉及如何安全地“空中换心”。

### 第二部分：核心架构补充 (Critical Supplements)

为了让这份蓝图真正“无懈可击”，建议补充以下四个维度的设计：

#### 2.1 IPC 总线选型：D-Bus + Shared Memory (混合总线)

EdgeX 使用 REST/Redis，我们在嵌入式 Linux 上必须更轻、更硬。

* **控制总线 (Control Bus)** -> **D-Bus (System Bus)**
* **理由**：Linux 标准，支持方法调用、信号广播、权限控制（PolicyKit）。
* **用途**：设备发现通知、配置更新、服务启停。
* **优势**：现有工具丰富（`dbus-monitor`），方便运维排查。


* **数据总线 (Data Bus)** -> **ZeroMQ (PUB/SUB) 或 NNG**
* **理由**：无 Broker 模式，纳秒级延迟，支持 `ipc://` (Unix Domain Socket) 传输。
* **用途**：高频遥测数据（Telemetry）的分发。


* **跨核通信 (AMP)** -> **OpenAMP / RPMsg**
* **补充**：针对 FOC/DSP 运行在 M 核的情况，A 核（Linux）需通过 `rpmsg_char` 设备驱动与 M 核交换控制指令。



#### 2.2 韧性设计：系统级看门狗与守护 (Systemd & Watchdog)

在工业级 C 框架中，**Crash 是常态，Recovery 才是能力**。

* **Systemd 深度集成**：
* 不要自己写 Daemon 管理。每个 Service（如 Modbus-Driver）都是一个 systemd unit。
* 配置 `Restart=on-failure`, `RestartSec=5s`。
* 启用 `WatchdogSec=10s`，服务必须定期向 systemd 发送 `sd_notify("WATCHDOG=1")`，否则会被硬件看门狗强制重启。


* **崩溃转储 (Coredump)**：
* 配置 `kernel.core_pattern`，配合 `systemd-coredump`。
* 当 SG-EL2025 在野外崩溃时，下次启动自动上传堆栈信息到云端。



#### 2.3 硬件隔离与实时性强化 (Isolation & RT)

针对 IEMS 和 SG-EL2025 的强实时需求，不能只靠 Preempt-RT。

* **CPU 隔离 (Isolcpus)**：
* 在 Bootargs 中配置 `isolcpus=3` (假设4核 CPU)。
* **关键策略**：将 Linux 的所有中断、SSH、日记等“杂事”绑定在 Core 0-2。
* **独占模式**：将 FOC 控制循环或 DSP 分析线程强制绑定（`pthread_setaffinity_np`）到 Core 3。**这是保证 10kHz 循环不抖动的唯一物理保障。**



#### 2.4 数据持久化的最后防线 (Power-Loss Safety)

SQLite WAL 很好，但还不够。工业现场经常直接断电。

* **文件系统**：对于 Flash 存储，必须强制使用 **UBIFS** 或 **F2FS**（带原子写支持）。
* **掉电保护策略**：
* 设计一个 **Power Manager 服务**，监听硬件的“掉电中断”（Power Fail Interrupt, PFI）。
* 电容通常能维持 100ms-500ms。
* **触发动作**：PFI 触发 -> `sqlite3_wal_checkpoint` (刷盘) -> `sync` -> 停止喂狗 -> 系统 Halt。

请告知团队，在具体编码时，**推荐**与**禁止**的技术栈：

* **✅ 推荐 (Adopt)**:

### 借鉴点一：系统级韧性 (Systemd 深度集成)

**观点提炼**：C 程序一定会挂，不要试图写出不挂的代码，要写出“挂了能秒级自动复活”的系统。
**借鉴动作**：放弃 SDK 内部自己写 Daemon/Fork，全面拥抱 **Systemd**。

#### 🛠️ SDK 改造方案

**1. 引入 `libsystemd` 依赖**
在 `CMakeLists.txt` 中链接 `libsystemd`。

**2. 改造 `Core Runtime` (SysRuntime)**
在 SDK 的主循环中加入“喂狗”逻辑。

```c
#include <systemd/sd-daemon.h>

// 在 edge_service_run 的主循环中
int edge_service_run(edge_service_t *svc) {
    // 1. 告诉 Systemd：我启动好了！
    sd_notify(0, "READY=1");

    // 2. 主循环
    while (!svc->stop_signal) {
        uv_run(svc->loop, UV_RUN_NOWAIT);

        // 3. 喂狗 (告诉 Systemd 我还活着)
        // Systemd 会检查 WatchdogSec，如果超时未收到，会杀掉并重启进程
        sd_notify(0, "WATCHDOG=1");

        // 4. 上报状态 (方便 systemctl status 查看)
        sd_notifyf(0, "STATUS=Processing data... Bus load: %d%%", bus_load);
    }

    sd_notify(0, "STOPPING=1");
    return 0;
}
```

**3. 部署文件 (`edge-core.service`)**
```ini
[Unit]
Description=EdgeOS Core Service
After=network.target

[Service]
Type=notify
ExecStart=/usr/bin/edge_core
WatchdogSec=10s
Restart=on-failure
RestartSec=5s
# 崩溃时自动转储 Core Dump
LimitCORE=infinity

[Install]
WantedBy=multi-user.target
```

### 借鉴点二：IPC 总线的具体选型 (NNG/ZeroMQ)

**观点提炼**：REST API 太慢，MQTT 内部用太重（序列化开销）。
**借鉴动作**：引入 **NNG (Nanomsg Next Gen)** 作为数据总线的默认实现。它比 ZeroMQ 更轻，且原生支持 C。

#### 🛠️ SDK 改造方案

**1. 扩展 `BusService` 实现 (`impl_nng.c`)**
使用 NNG 的 `PUB/SUB` 模式做遥测分发，`REQ/REP` 模式做内部控制。

```c
#include <nng/nng.h>
#include <nng/protocol/pubsub0/pub.h>

typedef struct {
    nng_socket sock;
} impl_nng_t;

static int nng_bus_init(bus_t *self) {
    impl_nng_t *impl = calloc(1, sizeof(impl_nng_t));

    // 使用 IPC (Unix Domain Socket)，零网络开销，纳秒级
    nng_pub0_open(&impl->sock);
    nng_listen(impl->sock, "ipc:///tmp/edge_telemetry.ipc", NULL, 0);

    self->impl_data = impl;
    return 0;
}

static int nng_bus_publish(bus_t *self, const char *topic, const DataPoint *dp) {
    impl_nng_t *impl = (impl_nng_t*)self->impl_data;

    // NNG 支持零拷贝发送 (nng_send 配合 NNG_FLAG_ALLOC)
    // 这里结合我们之前的 net_buf，可以做到极速分发
    nng_send(impl->sock, dp, sizeof(DataPoint), 0);
    return 0;
}
```

**2. 架构决策**
*   **控制面**（配置下发、启停）：使用 **D-Bus** (如果基于 Yocto) 或 **NNG REQ/REP**。
*   **数据面**（遥测）：使用 **NNG PUB/SUB** (IPC 模式)。
*   **超高速面**（AC 波形）：保持 **shm_ring** (共享内存) 不变。

### 借鉴点三：CPU 隔离与亲和性 (Isolcpus)

**观点提炼**：Linux 是分时的，只要有中断，实时线程就可能被打断。物理隔离是唯一的解药。
**借鉴动作**：在 SDK 中增加 **“CPU 亲和性 (Affinity)”** 配置接口。

#### 🛠️ SDK 改造方案

**1. 配置增强 (`edge_config_t`)**
增加 `cpu_affinity` 字段。

```json
{
  "services": {
    "iems_strategy": { "cpu_core": 3, "priority": 99 },
    "mqtt_export":   { "cpu_core": 0, "priority": 0 }
  }
}
```

**2. 线程绑定工具 (`core/utils_cpu.c`)**

```c
#define _GNU_SOURCE
#include <sched.h>
#include <pthread.h>

void edge_set_thread_affinity(int core_id) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core_id, &cpuset);

    pthread_t current_thread = pthread_self();
    if (pthread_setaffinity_np(current_thread, sizeof(cpu_set_t), &cpuset) != 0) {
        perror("pthread_setaffinity_np");
    }
}

void edge_set_rt_priority(int priority) {
    struct sched_param param;
    param.sched_priority = priority;
    // SCHED_FIFO: 只要我不主动让出 CPU，谁也别想抢
    pthread_setschedparam(pthread_self(), SCHED_FIFO, &param);
}
```

**3. IEMS/SG-EL2025 部署策略**
*   **Bootargs**: `isolcpus=3` (隔离第 4 个核，Linux 调度器不再往上面扔杂活)。
*   **App**: 在 IEMS 策略服务的 `init` 中，调用 `edge_set_thread_affinity(3)`。

### 借鉴点四：掉电保护 (Last Gasp)

**观点提炼**：文件系统损坏是设备返修的第一大原因。必须有“临终遗言”机制。
**借鉴动作**：新增 **PowerMgr Service**。

#### 🛠️ SDK 改造方案

**1. 新增服务接口 (`svc_power.h`)**
监听 GPIO 中断（来自 PMIC 或 电容电压检测电路）。

**2. 核心实现 (`src/services/power/impl_gpio.c`)**
使用 `libgpiod` 监听 PFI 引脚。

```c
#include <gpiod.h>

void on_power_fail_irq(int ev_type, void *data) {
    EdgeContext *ctx = (EdgeContext*)data;

    // 紧急处理流程 (必须在 100ms 内完成)

    // 1. 停止喂狗 (让硬件复位 IC 接管)
    systemd_stop_watchdog();

    // 2. 数据库强制 Checkpoint (刷 WAL 到磁盘)
    sqlite3_wal_checkpoint_v2(ctx->db, NULL, SQLITE_CHECKPOINT_FULL, NULL, NULL);

    // 3. 停止所有写操作
    ctx->storage_readonly = 1;

    // 4. 同步文件系统元数据
    sync();

    // 5. 记录最后一条日志 "POWER FAIL"
    zlog_fatal(ctx->logger, "Power failure detected! System halted.");
}
```
