# 05 P0 最小可验证切片

状态：设计基线，待评审。未实现。

## 1. 目的

这不是演示，是证伪。P0 只验证三个最关键的假设：

1. 注册表事务模型在真实故障下是否自洽。
2. 能力申请与授权链路能否拦住越权，并且撤销立即生效。
3. WASM 单实例故障是否真的不扩散，宿主崩溃后能否恢复。

三个假设都成立，才允许扩展贡献类型和语言。

## 2. 范围

| 维度 | P0 取值 | 明确不做 |
| --- | --- | --- |
| 运行时 | 一个 WASM 运行时（WAMR 或 wasmtime，按第 04 号文档的判据二选一） | QuickJS、Go sidecar、Python |
| 语言 | C | C++、Rust、Go |
| 贡献类型 | `telemetry.points`，只读 | `ui.pages`、`northbound.metrics`、`alarm.rules`、`schedule.jobs`、`protocol.handlers` |
| 能力 | `tags.read` 单点位、`log` | `tags.write`、`alarm.raise`、`net.egress` |
| 界面 | 无应用页面，只有一个只读的状态接口 | 应用商店前端、详情页 |
| 签名 | 一个测试密钥，真实验签 | 密钥轮换、证书链 |
| 分布 | 本地安装包，不经网络 | 商店后端、远程下载 |

## 3. 组件

四个新组件，全部是最小实现。

1. `app-manager`：单写者，负责安装、批准、启动、停止、卸载、回滚，写注册表与快照。
2. `app-host`：WASM 宿主进程，加载实例，提供 Host ABI，做配额与故障处理。
3. `registry-snapshot`：从注册表生成 `gen-N.json` 并原子发布，供只读消费。
4. `appctl`：命令行，用于安装、批准、启停、查看状态。P0 不做 WebUI。

对现有代码的改动只允许两处：DataHub 点位元数据从静态数组改成可增删注册表；启动流程加一个 app-manager 与 app-host 的拉起。其他子系统不动。

## 4. 接口

命令行足够验证，不做 Web 接口。

```
appctl install <pkg> --key <pub>      # 验签、校验、暂存、提交
appctl grant <app> <cap> --scope <s>  # 批准能力
appctl revoke <app> <cap>
appctl start <app>
appctl stop <app>
appctl upgrade <app> <pkg>
appctl rollback <app>
appctl uninstall <app>
appctl status [<app>]
appctl snapshot                        # 打印当前 generation 与贡献摘要
```

状态接口 `appctl status` 输出机器可读 JSON，供验收脚本断言。

## 5. 交付物

1. `app.yaml` 的 JSON Schema v1。
2. WIT 包 v1，只含 `tag_read`、`log`、`now_ms`。
3. C 绑定，由 WIT 生成，CI 校验不可手改。
4. 注册表 schema 与快照格式说明。
5. 一个示例 C 应用：订阅一个点位，值超阈值时写日志。
6. 验收脚本，逐条执行第 6 节的检查并输出证据文件。
7. 一份故障注入脚本，覆盖第 01 号文档列出的 10 个中断点。

## 6. 验收项与证据

每一条都要有可复现的命令和输出，不接受"人工观察"。

| # | 检查 | 证据 |
| --- | --- | --- |
| 1 | 两份错误清单被拒：含通配符能力、未知贡献类型 | 退出码与错误码 |
| 2 | 未签名包被拒 | 退出码与错误码 |
| 3 | 只读能力未批准时，应用可安装但不可启动 | 状态 JSON 中 `state=installed`、`start` 返回拒绝 |
| 4 | 批准后可启动，读授权点位成功 | 应用日志与状态 JSON |
| 5 | 读未授权点位返回 `denied_not_granted` | 错误码与审计记录 |
| 6 | 撤销后 200ms 内下一次读取返回 `denied_revoked` | 时间戳对比 |
| 7 | 死循环触发中断，实例 `faulted`，同宿主其他实例仍在运行 | 两个实例的状态与日志 |
| 8 | 内存超限实例失败，宿主存活 | 状态 JSON 与宿主 pid 未变 |
| 9 | `kill -9 app-host` 后 5 秒内恢复，应用重新激活 | 时间戳与状态 JSON |
| 10 | 安装时在第 3 步与第 5 步之间断电，重启后无半套贡献 | 重启前后的快照摘要对比 |
| 11 | 补偿执行到一半断电，重启后重放完成 | 快照摘要与 txn 日志 |
| 12 | 升级后回滚，贡献集合与升级前逐条相等 | 快照 diff 为空 |
| 13 | 卸载后点位名仍可解析，写入被拒 | 历史查询返回与写入错误码 |
| 14 | 两个并发安装，一个成功一个 `already_installed` | 两次退出码 |
| 15 | 手改 C 绑定，CI 失败 | CI 日志 |

第 10 到 12 条是 P0 的核心，前 9 条只是前置条件。

## 7. 退出条件

全部满足才进入 P1：

- 15 项验收全过，证据归档。
- 故障注入脚本可在 CI 中重复运行，结果稳定。
- 没有一项检查依赖人工判断。
- 注册表在 10 个中断点上的最终状态与第 01 号文档的矩阵完全一致。
- 目标板上侧写一次：CPU 占用、内存占用、安装耗时、启动耗时、恢复耗时。数字归档，不写进承诺。

任何一条不满足，P0 范围不变，先修机制，不加功能。

## 8. 明确不在 P0 内

- 应用商店界面与安装体验。
- 北向自动上送。
- 告警规则。
- Go、Python、JS。
- 签名基础设施与密钥管理。
- 多设备分发、灰度、回滚编排。
- 性能指标承诺。

## 9. 风险

- 目标板上的 WASM 运行时可能不支持所选的中断机制，选型需要在第一天确认，否则整个 A 档要重做。
- 掉电注入在真实硬件上可能不可控，需要可编程电源或内核级注入，测试环境要先具备。
- DataHub 点位表改成可增删注册表，可能影响现有北向与历史查询的启动顺序，需要在 P0 内先做一次兼容性验证。
- 5 秒恢复目标是判断，不是测量。若实测明显更慢，需要重新评估"宿主进程崩溃可接受"这一前提。
