# 10 产品点位剖面与应用命名空间

状态：设计基线，待评审。未实现。

## 1. 问题

文档只规定了应用自己发布的 `app.<id>.<point>`，没有规定应用怎么引用**产品点位**。02 的示例写 `tags.read: [U_A]`，但 `U_A` 是谁定义、在 DCU 与 IEMS 上是否同名、能不能稳定，全文没有答案。

后果很具体：DCU 用 698 OAD，IEMS 用寄存器与 BMS 电芯。一个"电压越限"应用要么为每个产品打一个包，要么平台提供一层语义名。前者是 N×P，后者才可能做到 N+M。

## 2. 两个命名空间，边界固定

| 命名空间 | 例子 | 谁定义 | 何时变化 |
| --- | --- | --- | --- |
| 产品点位 | `product.dcu.voltage.a` | 产品构建期，静态剖面 | 随产品固件版本 |
| 应用点位 | `app.voltage_guard.sag_count` | 应用清单，安装时注册 | 随应用版本 |

两者不重叠：产品点位不得以 `app.` 开头，应用点位不得以 `product.` 开头，注册时校验。应用不能覆盖或影子任何产品点位。

## 3. 产品点位剖面

每个产品发布一份**静态、带版本**的剖面。剖面是产品代码里的 C 结构体，构建期生成，不是运行期 YAML/JSON。这一点与 ADR-0010、`COMPONENT_CLASSIFICATION` 的"点表静态、manifest 不进运行时"一致。

```c
typedef struct {
    const char *name;        /* "voltage.a" */
    uint8_t     type;        /* double / int64 / bool */
    const char *unit;        /* "V" */
    uint16_t    native_kind; /* OAD / register / BMS cell */
    uint32_t    native_id;
} product_point_t;

typedef struct {
    const char *profile;     /* "dcu@1" */
    const product_point_t *points;
    size_t count;
} product_profile_t;
```

剖面的规则：

- `profile` 是 `产品@主版本`。主版本变化表示语义不兼容（改名、改单位、改类型）。
- 剖面是静态的，运行期只读。应用不能新增、修改或删除产品点位。
- 单位与类型随剖面走。应用声明期望类型，解析时校验，不匹配拒绝。
- 一个产品可以同时发布多个版本剖面（`dcu@1`、`dcu@2`），迁移期内并存。

## 4. 应用怎么引用

```yaml
requires:
  product: dcu@1
  points:
    - name: product.dcu.voltage.a
      type: double
      unit: V
```

- `requires.product` 决定这个包只能装在剖面匹配的产品上，安装期校验，不匹配拒绝。
- 一个包要支持多个产品，声明列表：`products: [dcu@1, iems@1]`。每个产品仍需各自的剖面，应用不能用一套名字跨产品猜。
- 运行期解析由 **infra 层的共享 resolver** 完成：它持有当前产品剖面，把 `product.<product>.<name>` 解析成原生标识，再调用产品端口。产品只提供静态剖面与端口实现，不重写解析逻辑。
- 解析结果带 `(profile, native_kind, native_id)`，授权按解析后的原生标识校验。

这样"应用读产品点位"在每个产品上只增加一张静态剖面，不增加一份解析代码。N 个产品加 P 个应用，工作量是 N+P，不是 N×P。

## 5. 与 ADR-0010/0011 的关系

`COMPONENT_CLASSIFICATION` 写的是"点表由产品防腐层用极简静态 C 结构体维护，不引入 JSON/YAML 配置层；manifest 不作为运行时输入"。

本设计不违反这一点，但需要把边界写进 ADR 修订提案，因为"应用点位"确实是动态的。修订提案要明确三件事：

1. **应用点位是静态点表之外的独立动态命名空间**，由注册表维护，不进入产品静态点表。
2. **边界与互不覆盖规则**：`product.` 与 `app.` 前缀隔离，应用不能影子产品点位；产品剖面静态，应用贡献动态。
3. **解析发生在 infra 层**：共享 resolver 读静态剖面，产品只提供剖面与端口；运行期不解析 YAML/JSON 点表。

在这三点写入 ADR 修订之前，P0 不应选定点位承载路径。修订提案草案见本文件第 8 节。

## 6. 命名文法

统一规则，避免 `app.a.b.c` 的归属歧义：

- `app-id`：`[a-z][a-z0-9-]{0,62}`，不含点号，不含大写。
- 应用点位名：`[a-z][a-z0-9_]{0,62}`，不含点号。
- 应用点位完整名固定三段：`app.<app-id>.<point-name>`。
- 产品点位完整名：`product.<product-id>.<name>`，`name` 允许点号分段，但必须以剖面里登记的完整名为准。
- 全部小写，不做 Unicode 归一化，非 ASCII 一律拒绝。注册时校验。

## 7. 验收

1. 装在剖面不匹配的产品上，安装被拒，错误可读。
2. 应用引用剖面里不存在的产品点位，安装或解析被拒。
3. 类型或单位与剖面不符，拒绝解析。
4. 应用注册 `app.` 之外的点位，或产品点位以 `app.` 开头，注册被拒。
5. 两个应用注册同名应用点位，后者被拒。
6. 应用点位名含点号、大写或非 ASCII，注册被拒。
7. 同一应用声明支持 `dcu@1` 与 `iems@1`，两个产品各自解析到正确原生标识。
8. 产品剖面主版本升级后，旧应用在迁移期内仍可解析旧剖面。
9. 解析逻辑只有一份，位于 infra；产品目录下没有重复实现。
10. 运行期不读取任何 YAML/JSON 点表。

## 8. ADR 修订提案草案

标题：应用平台引入独立于产品静态点表的动态命名空间

要写清的四点：

1. 产品静态点表与产品剖面保持构建期静态，运行期只读。
2. 应用点位由注册表维护，前缀 `app.`，与产品点位前缀隔离，互不覆盖。
3. 解析由 infra 共享 resolver 完成；产品只提供剖面与端口。
4. 授权按解析后的原生标识与调用方身份校验，强制点在产品 ACL。
