# 10 产品点位剖面与应用命名空间

状态：第二轮修订（2026-11-09/10），待复审。未实现。

## 1. 问题

文档只规定了应用自己发布的 `app.<id>.<point>`，没有规定应用怎么引用**产品点位**。02 的示例写 `tags.read: [U_A]`，但 `U_A` 是谁定义、在 DCU 与 IEMS 上是否同名、能不能稳定，全文没有答案。

后果很具体：DCU 用 698 OAD，IEMS 用寄存器与 BMS 电芯。一个"电压越限"应用要么为每个产品打一个包，要么平台提供一层语义名。前者是 N×P，后者才可能做到 N+M。

## 2. 两个命名空间，边界固定

| 命名空间 | 例子 | 谁定义 | 何时变化 |
| --- | --- | --- | --- |
| 产品点位 | `product.dcu.area.voltage.min` | 产品构建期，静态剖面 | 随产品固件版本 |
| 应用点位 | `app.voltage_guard.sag_count` | 应用清单，安装时注册 | 随应用版本 |

两者不重叠：产品点位不得以 `app.` 开头，应用点位不得以 `product.` 开头，注册时校验。应用不能覆盖或影子任何产品点位。

## 3. 产品点位剖面

每个产品发布一份**静态、带版本**的剖面。剖面是产品代码里的 C 结构体，构建期生成，不是运行期 YAML/JSON。这一点与 ADR-0010、`COMPONENT_CLASSIFICATION` 的"点表静态、manifest 不进运行时"一致。

```c
typedef struct {
    const char *name;        /* "voltage.a" */
    uint8_t     type;        /* double / int64 / bool */
    const char *unit;        /* "V" */
    double      min;         /* 量程下限，必填 */
    double      max;         /* 量程上限，必填 */
    double      scale;       /* 倍率，默认 1.0；北向编码用 */
    uint16_t    native_kind; /* OAD / register / BMS cell */
    uint32_t    native_id;
} product_point_t;

typedef struct {
    const char *profile;     /* "dcu@1" */
    const product_point_t *points;
    size_t count;
} product_profile_t;
```

剖面的规则：

- `profile` 是 `产品@主版本`。主版本变化表示语义不兼容（改名、改单位、改类型、改量程）。
- 剖面是静态的，运行期只读。应用不能新增、修改或删除产品点位。
- 单位与类型随剖面走。应用声明期望类型，解析时校验，不匹配拒绝。
- **量程与质量码（2026-11-09 已定）**：`type`、`unit`、`min`、`max` 必填，`scale` 可选（默认 1）；质量统一 good/bad/uncertain 三态，不接受厂商自定义码。量程用于安装校验、UI 合法区间与北向倍率编码；运行时越界不拒绝，标 `uncertain` 并告警。
- **v1 不做 enum 点位**：需要状态量时先用 bool + 产品侧映射，等真实 OAD 需求再设计。
- 一个产品可以同时发布多个版本剖面（`dcu@1`、`dcu@2`），迁移期内并存。

### 设备维（2026-11-09 已定）

**v1 剖面只暴露产品级聚合点，不引入“设备”维。** 例如 DCU 暴露 `product.dcu.area.voltage.min/avg/max` 三个台区聚合点，由 DCU 产品侧计算并维护；应用读不到“某只表的 A 相电压”。

理由：DCU 有 4096 只表，把设备维引进应用 ABI 会让剖面、授权、句柄、历史键全部多一维；第一版应用要的是台区级统计，聚合点足够。每表点位留给后续的 `per_device` 贡献类型，等有真实应用要“看某只表”时再开，并单独设计设备组、枚举权限与历史键。

`product_point_t` 因此只描述“一个产品级点位”，不是“一个设备实例上的点位”。`native_kind` / `native_id` 指向产品内部实现（如聚合槽位或 OAD 常量），不暴露设备地址。

## 4. 应用怎么引用

```yaml
requires:
  products: [dcu@1]
  points:
    - name: product.dcu.area.voltage.min
      type: double
      unit: V
```

- `requires.products` 决定这个包只能装在剖面匹配的产品上，安装期校验，不匹配拒绝。
- 一个包要支持多个产品，直接加列表：`products: [dcu@1, iems@1]`，前提是这些产品的点位名与语义完全相同。语义不同就分别构建：同一个 `app_id`、不同包，各自 `products` 只列一个产品；设备上只会装其中一份，不会冲突。应用不能用一套名字跨产品猜语义。
- 运行期解析由 **产品 ACL 内的 resolver** 完成：它是链接进各产品的同一个 C 库，各产品带自己的静态剖面表，把 `product.<product>.<name>` 解析成原生标识，再调用产品端口。不是新的全局进程，也不是 infra 服务。产品只提供静态剖面与端口实现，不重写解析逻辑。
- 解析结果带 `(profile, native_kind, native_id)`，授权按解析后的原生标识校验。

这样"应用读产品点位"在每个产品上只增加一张静态剖面，不增加一份解析代码。N 个产品加 P 个应用，工作量是 N+P，不是 N×P。

## 5. 与 ADR-0010/0011 的关系

`COMPONENT_CLASSIFICATION` 写的是"点表由产品防腐层用极简静态 C 结构体维护，不引入 JSON/YAML 配置层；manifest 不作为运行时输入"。

本设计不违反这一点，但需要把边界写进 ADR 修订提案，因为"应用点位"确实是动态的。修订提案要明确三件事：

1. **应用点位是静态点表之外的独立动态命名空间**，由注册表维护，不进入产品静态点表。
2. **边界与互不覆盖规则**：`product.` 与 `app.` 前缀隔离，应用不能影子产品点位；产品剖面静态，应用贡献动态。
3. **解析发生在产品 ACL**：resolver 读静态剖面，产品只提供剖面与端口；运行期不解析 YAML/JSON 点表。解析逻辑是一份共享 C 库，不是全局进程。
4. **值由 DataHub 承载，但名字不归 DataHub**：注册表给应用点位分配槽位，产品进程计算 `app_tag = app_base + slot`；DataHub 用 `map_fn < 0 → idx = tag_id` 的既有回退路径存值。槽位是设备内 infra 编号，不暴露给应用、北向或外部协议；应用只见 `app.<id>.<point>`。

**槽位区（2026-11-09 已定）。** 应用区固定 4096 槽，`app_base = 产品容量`（DCU 为 131072）；每个应用连续分配 256 槽，点位超过 256 则安装拒绝并提示拆分，4096 槽支持 16 个满配额应用。容量常量由同一份生成常量提供给 C 与 Go 镜像，CI 检查一致，不再各自硬编码 1024/16384。产品 `map_fn` 对 `tag_id >= app_base` 返回 `<0>`，走 `idx = tag_id` 回退；DCU 的 `dcu_tag_map_fn` 必须先改这一行，否则应用点位会落进 `device_id × 32 + slot` 公式。卸载可回收槽位，历史不按槽位存，回收不影响查询。

点位承载路径已于 2026-11-09 选定；上述四条写入 ADR 修订并经评审后冻结。修订提案草案见本文件第 9 节。

## 6. 命名文法

统一规则，避免 `app.a.b.c` 的归属歧义：

- `app-id`：`[a-z][a-z0-9-]{0,62}`，不含点号，不含大写。
- 应用点位名：`[a-z][a-z0-9_]{0,62}`，不含点号。
- 应用点位完整名固定三段：`app.<app-id>.<point-name>`。
- 产品点位完整名：`product.<product-id>.<name>`，`name` 允许点号分段，但必须以剖面里登记的完整名为准。
- 全部小写，不做 Unicode 归一化，非 ASCII 一律拒绝。注册时校验。

## 7. 北向暴露（2026-11-09 方向已定）

v1 应用点位**只本地可见**（UI、其他应用、状态接口），不自动上送北向。原因：DCU 的 698.45 主站按固定 OAD 寻址，应用点位是动态的，没有 OAD；不能要求现场主站为每个新应用改对象模型。

方向（`northbound.metrics` 落地时采用）：**产品预留一段静态北向槽位。** 例如 DCU 在厂商自定义 OI 下预留 64 个 OAD，槽位号固定在产品剖面；注册表把应用点位分配到槽位，管理员在 UI 里把点位绑到槽位，主站侧按同一张表配置一次。新应用只填槽，不改主站对象模型。

**槽位规则（2026-11-10 已定）。**

1. 每产品 64 个静态 OAD 槽；槽位用完拒绝新映射，提示先回收，不动态扩容。
2. **只读遥测**：北向只读，应用点位的写/控制不走北向，避免主站成为第二个授权入口。
3. **卸载不删槽**：应用卸载后槽位标 `invalid`，主站读质量 `bad`；不删除槽位、不复用给别的应用，除非管理员显式"回收并重新映射"并写审计。
4. **映射表**：`northbound_slot(product, slot) -> app_id, point_name, contract_version, oad, scale`，与控制库同事务写入；快照 generation 变化时北向重读。
5. 这条不进入 P0；实现细节（主站点表同步、无效值编码）随 `northbound.metrics` 单独评审。

## 8. 验收

1. 装在剖面不匹配的产品上，安装被拒，错误可读。
2. 应用引用剖面里不存在的产品点位，安装或解析被拒。
3. 类型或单位与剖面不符，拒绝解析。
4. 应用注册 `app.` 之外的点位，或产品点位以 `app.` 开头，注册被拒。
5. 两个应用注册同名应用点位，后者被拒。
6. 应用点位名含点号、大写或非 ASCII，注册被拒。
7. 同一应用声明支持 `dcu@1` 与 `iems@1`，两个产品各自解析到正确原生标识。
8. 产品剖面主版本升级后，旧应用在迁移期内仍可解析旧剖面。
9. 解析逻辑只有一份，位于 infra；产品目录下没有重复实现。
10. 运行期不读取任何 YAML/JSON 点表。
11. 应用引用 `product.dcu.meter.<addr>.voltage.a` 这种带设备维的名字，v1 解析被拒，错误码可读。
12. DCU `dcu@1` 剖面包含 `area.voltage.min/avg/max`，类型与单位校验通过；应用读不到单表点位。

## 9. ADR 修订提案草案

标题：应用平台引入独立于产品静态点表的动态命名空间

要写清的四点：

1. 产品静态点表与产品剖面保持构建期静态，运行期只读。
2. 应用点位由注册表维护，前缀 `app.`，与产品点位前缀隔离，互不覆盖。
3. 解析由产品 ACL 内的共享 C 库完成；产品只提供剖面与端口，不新建全局进程。
4. 授权按解析后的原生标识与调用方身份校验，强制点在产品进程。
5. 应用点位的值经 DataHub 槽位承载；槽位由注册表分配、可回收，是 infra 编号，不是公共身份；历史不按槽位存。

状态：已选定，ADR 修订待提交评审；评审通过后冻结。
