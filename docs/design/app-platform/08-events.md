# 08 事件模型：不造通用总线

状态：设计基线，待评审。未实现。

## 1. 结论

**不新增通用事件总线。** 现有四类通道已经覆盖数据、控制、浏览器和宿主四个面，缺的只有一条很小的"平台到应用"事件通道，补上即可。

通用总线听起来省事，实际会把授权、类型、投递语义和背压四件事同时变成平台要解决的问题。iOS 和 VS Code 都没有走这条路，值得先看清楚它们为什么没有。

## 2. 手机端和 VS Code 的事实

**iOS 没有跨应用事件总线。** 应用之间能做的只有几件事：URL Scheme 打开另一个应用、App Group 共享容器（同一开发者）、XPC 调系统服务、扩展与宿主应用共享容器。`NotificationCenter` 是进程内的，不是跨应用。系统级的 Darwin 通知只有名字没有载荷，且不是给第三方做业务分发的。隔离优先，宁可少一种能力。

**VS Code 没有正式的跨扩展事件总线。** 所有扩展跑在同一个扩展宿主进程里，通过 `vscode.commands` 调彼此的命令，通过 `vscode` API 的事件（文档变化、配置变化）反应。这是一种共享进程加命令注册表的弱总线，隔离性也弱。语言服务器之间走的是各自独立的 JSON-RPC，不是共享总线。

**Android 的广播最接近总线**，但也正因为如此，隐式广播、后台启动、包可见性在多个版本里被逐步收紧。这是"总线能力一旦放开就很难收回"的例子。

共同点：成熟平台给的是**有类型、有权限的接口**，不是一条谁都能往里塞消息的管道。

## 3. 现有的四条通道

不需要新造，仓库里已经有四条，各自解决一类问题。

| 通道 | 实现 | 解决的问题 | 语义 |
| --- | --- | --- | --- |
| 数据面 | DataHub 的 `datahub_subscribe_tag` / `subscribe_domain` / `subscribe_filtered` | 遥测与应用点位的值变化 | 保留最新值；可按死区与仅变化订阅；回调在宿主线程 |
| 控制面 | 注册表 generation 与消费者偏移（01 号文档） | 安装、升级、卸载、授权变化 | 不可变快照；至少一次；消费者幂等 |
| 浏览器面 | `/api/v1/ws` 的 `alarm`、`task`、`config-transaction`、`telemetry` 主题 | WebUI 实时刷新 | 带序号；发现缺号即 resync；服务端不保留积压 |
| 宿主面 | app-host 的每应用事件队列（04 号文档） | 把点位变化与平台事件送到应用 | 有界队列；满则丢最旧并计数；不阻塞生产者 |

浏览器面已经证明了一个重要取舍：**事件不是真相**。断线或漏号时，消费者整体重取，而不是拿事件回放。应用平台沿用这个取舍，不引入"事件必须全部送达"的承诺。

## 4. 需要补的一条：平台到应用的事件

应用需要知道几件平台侧的变化，否则只能轮询。这条通道只允许平台发、应用收，不开放给应用之间。

| 事件 | 载荷 | 应用应该做什么 |
| --- | --- | --- |
| `settings.changed` | 变更的键名，不含值 | 重新读取设置 |
| `grant.changed` | 能力、范围、授予或撤销 | 撤销时停止相关操作，重新校验 |
| `upstream.available` | 点位名 | 之前降级的读取可以重试 |
| `upstream.unavailable` | 点位名 | 标记数据不可用，不要等到超时 |
| `registry.generation` | 新代次 | 重新读取自己关心的贡献与点位 |
| `app.will_stop` | 原因、剩余毫秒 | 落盘、释放资源 |

统一信封：

```
event_id    ULID，应用用于幂等
type        上表之一
version     事件 schema 版本
ts          宿主单调时钟与墙钟
app_id      目标应用
payload     类型化载荷
```

投递语义：

- 至少一次，按应用内顺序投递。
- 队列有界，满则丢最旧并计数，同时记一条日志。丢事件不是数据丢失，因为事件都对应可重读的状态。
- 应用按 `event_id` 去重。重启后不补发历史事件；应用启动时自己读一次设置、授权、点位表，把状态对齐。
- 应用不能订阅其他应用的事件，也不能发布事件。没有 `app.<id>.>` 这种主题。

这条通道的实现很小：一个按应用分队列的扇出器，加六个事件类型的编码。不需要 broker。

## 5. 应用发出去的东西

应用想通知别人，不用事件，用已有机制：

| 想做的事 | 用什么 | 为什么不用事件 |
| --- | --- | --- |
| 发布派生数据 | `telemetry.points` | 点位有类型、有保留、有授权 |
| 触发告警 | `alarm.raise` | 告警有级别、确认、审计 |
| 让页面刷新 | 点位变化自动推送到浏览器 | 浏览器面已有主题与 resync |
| 触发另一个应用 | 发布点位，对方订阅 | 直接事件会把两个应用的生命周期绑死 |

## 6. 应用之间为什么不给总线

四条理由，任何一条都足以否决。

1. **绕过授权与类型。** 总线一旦能发任意主题与载荷，应用就多了一条不需要批准的数据通道。第 02 号文档的逐次校验会被绕开。
2. **主题变成 API。** 一旦有应用订阅 `app.a.events`，这个主题就成了对外契约，改名、改载荷都要考虑所有订阅者，回到"装 B 要改 A"。
3. **投递语义失控。** 顺序、重放、保留、背压、慢消费者，一旦承诺就要实现，最后变成在网关上造一个小型消息中间件。
4. **可观测性变差。** 点位进历史、告警进审计、控制面进 generation；总线上的消息没有归属，出问题无法追溯。

需要协作时，走点位。发布方不知道谁在消费，消费方不需要发布方为它改动。这是第 06 号文档已经定下的规则。

## 7. 什么情况下重新考虑

给触发条件，不给"以后再说"。

- 出现三个以上生产者向 N 个消费者扇出，且需要按属性过滤，而不是按点位名。
- 需要跨重启的持久重放，且事件本身是唯一真相，不能从状态重读。
- 需要跨设备分发，超出单网关范围。
- 点位模型的类型与保留策略无法表达这类数据。

任一条件成立时，**先评估复用已有 MQTT 设施**（北向已经在用），而不是在网关里新写一个 broker。仍然不做的：应用直接持有 broker 凭据、应用自定义主题。

## 8. 语义总表

| 通道 | 投递 | 保留 | 顺序 | 消费者拿不到时 |
| --- | --- | --- | --- | --- |
| 数据面 | 变化即回调 | 最新值 | 按点位 | 读影子值为准 |
| 控制面 | 至少一次 | 全量快照 | 按 generation | 重读当前代 |
| 浏览器面 | 至少一次 | 无积压 | 全局 seq | 收到缺号即 resync |
| 宿主面 | 至少一次 | 队列内 | 应用内 | 启动时重读状态 |

四行有一个共同点：**状态可重读，事件只用来降低延迟**。这条原则决定了不需要持久总线。

## 9. 验收

1. 修改设置后，运行中的应用在 1 秒内收到 `settings.changed`，读到新值。
2. 撤销授权后，应用收到 `grant.changed`，下一次调用返回 `denied_revoked`。
3. 上游应用安装后，等待中的应用收到 `upstream.available`，不需要重启。
4. 上游应用停止后，收到 `upstream.unavailable`，读取不再阻塞。
5. 事件队列打满，丢弃计数增长，生产者不被阻塞，应用仍能运行。
6. 重复投递同一 `event_id`，应用侧只处理一次。
7. 伪造来自其他应用的事件，投递被拒绝并记审计。
8. 应用尝试订阅任意主题，接口不存在，返回参数错误。
9. 应用重启后不补发历史事件，但设置、授权、点位状态与服务端一致。
10. 浏览器断线重连后收到缺号 resync，页面状态与快照一致。

## 10. 未决

- `app.will_stop` 的剩余时间给多少，取决于 sidecar 的优雅停止窗口。
- 事件队列容量与丢弃策略是否需要按应用配置，还是统一初值。
- 是否需要把平台事件也镜像成点位，让 WebUI 不新开一条通道。目前倾向不镜像，避免把控制面事件混进遥测。
- MQTT 复用作为未来触发条件下的候选，需要先评估离线设备的凭据管理。
