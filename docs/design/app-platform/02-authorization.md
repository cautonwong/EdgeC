# 02 授权模型：声明、批准、执行、撤销

状态：设计基线，待评审。未实现。

## 1. 结论先行

清单里的 `capabilities` 是**申请**，不是授权。授权来自三条同时成立：管理员批准、宿主策略允许、运行时逐次校验通过。任何一条不成立，调用被拒绝并留审计。

"能力即权限"把申请当成授权，是本设计明确否决的简化。声明与授权必须分开，见下一节。

### 威胁模型

按 STRIDE 对五个边界各看一遍，每一项都要有对应控制，不能只写"由权限系统保证"。

| 威胁 | 边界 | 具体场景 | 控制 |
| --- | --- | --- | --- |
| 仿冒 | 包 | 冒充官方应用 | 签名覆盖清单与文件摘要；grant 绑定包摘要 |
| 篡改 | 包 / 清单 | 安装后替换文件 | 加载前重新校验摘要；摘要不符拒绝启动 |
| 抵赖 | 批准 | 管理员否认批过写权限 | 审计记录批准人、时间、范围、工单 |
| 信息泄露 | 点位 | 应用读未授权点位 | 逐次校验；默认拒绝；无环境授权 |
| 拒绝服务 | 运行时 | 死循环、内存炸弹、调用风暴 | 看门狗、配额、Host 调用预算、导入白名单 |
| 提权 | 授权 | 用启停权换取批准权；通配符扩大范围 | 批准权与启停权分离；禁止通配；禁止自批 |
| 重放 | 下行 | 重放旧的控制命令 | 命令带时间戳与序列号；网关侧幂等键 |
| 供应链 | 包 | 降级到有漏洞的旧版本 | 版本只增不减；降级需显式操作并审计 |

"混淆代理人"是这里最容易被忽略的一项。应用不能把自己的权限借给另一个应用，也不能让宿主替它执行未授权的操作。Host ABI 每次调用都带实例身份，宿主不做"调用方未声明但看起来合理"的推断。

## 2. 四层分离

| 层 | 由谁产生 | 存在哪里 | 能改变什么 |
| --- | --- | --- | --- |
| 申请 | 应用作者，写进 `app.yaml` | `app_version.manifest` | 只决定"能申请什么" |
| 批准 | 管理员，显式操作 | `grant` 表，绑定版本与包摘要 | 决定"实际给了什么" |
| 策略 | 设备所有者，设备级配置 | 策略文件，随固件或运维下发 | 决定"这类申请现在允不允许" |
| 执行 | 宿主，每次 Host 调用 | 运行时内存中的授权快照 | 决定"这一次放不放行" |

四层的顺序不能颠倒。批准不能绕过策略，执行不能绕过批准。

## 3. 能力模型

能力按资源类型分组，每个能力带范围。范围是必须的，不接受"申请全部"。

```yaml
capabilities:
  tags:
    read:  [U_A, U_B]        # 明确点位，不支持通配
    write: []
  alarms:
    raise: [power.voltage]   # 明确规则类型
  kv: {}
  schedule:
    jobs: []
  net:
    egress: []               # 默认空，即禁止
```

v1 只开放 `tags.read`（单点位）、`kv`、`log`。`tags.write`、`alarms.raise`、`net.egress` 在 P0 之后单独评审。

通配符只允许出现在宿主策略里，不允许出现在应用清单里。应用写 `U_*` 直接判为非法清单。范围里的点位名由产品 ACL 解析，不注册新的全局数字 TagID（ADR-0010）。

## 4. 批准流程

```
申请(manifest)
   │
   ├─ 静态检查：范围是否合法、是否含通配、是否属 v1 开放集
   │      └ 不通过 → 拒绝安装，不产生 grant
   │
   └─ 全部能力 → grant 状态 pending，应用可安装但不可启动
          └ 管理员批准 → granted；拒绝 → denied，可卸载
```

**P0 固定关闭只读自动授权。** P0 的所有 grant 都必须经 `appctl grant` 显式批准，以便验证授权链路本身。只读自动授权是 P0 之后单独决策的策略，不在本节默认开启。

写能力不接受自动批准。批准写能力必须满足：

1. 操作者具备 `app.approve_write` 权限。
2. 触发**双人复核**，复用现有双人授权服务，不新造一套。全文统一用"双人复核"，不再使用"二次确认"这类会与普通确认混淆的说法。
3. 记录工单号或原因，为空拒绝。
4. 设备不处于"调试窗口期"以外的宽松模式。

**离线设备的双人复核。** 现场经常没有网络，不能依赖远程审批。规则是：两名不同的本地账号都具备 `app.approve_write`，在同一台设备上分别输入各自凭据，两次输入间隔不超过 5 分钟，且发起人不能是复核人。两次凭据都通过本地校验后写入一条审批记录，记录两个账号与时间。没有网络也能完成，但必须有两个人。

**撤销的耐久性。** 授权撤销与审计写入使用 `synchronous=FULL`（详见 01 号文档），落盘后才返回成功。否则掉电会把已撤销的能力复活，这比丢一条安装记录严重得多。

### 权限生命周期

参照 Android 与 iOS 的做法，权限不是一次性永久授予，而是有生命周期和可见状态。网关场景的差别是没有应用运行时的用户弹窗，所以把"运行时征得同意"换成"安装与批准时显式确认，运行期可查可撤"。

| 类型 | 例子 | 授予方式 | 有效期 |
| --- | --- | --- | --- |
| 普通 | 读单点位、写命名空间 KV | 管理员一次批准 | 长期，可撤销 |
| 敏感 | 写点位、发告警 | 管理员 + 双人复核 | 长期，可撤销，需工单 |
| 一次性 | 读取一次诊断快照 | 批准后首次调用即失效 | 单次 |
| 限时 | 调试窗口内的写操作 | 管理员批准 | 到期自动失效 |

- 敏感能力必须可单独撤销，不能只能整个应用卸载。
- 应用页面显示已授予、待批准、已暂停、已撤销四种状态，以及每项的批准人与时间。
- 撤销立即生效，下一次调用返回 `denied_revoked`，并在应用日志中可见。
- 不允许"一键全授权"。批量批准只能逐个勾选，避免管理员在不看范围的情况下放过全部。
- 授权不能复制给另一个应用。克隆应用时授权全部重新走批准流程。

**暂停状态。** 升级与回滚需要第五种状态：`suspended`。升级时旧版本的 grant 转 `suspended`，保留审批记录但不生效；回滚到旧版本时恢复为 `granted`，不需要重新审批。新版本仍然必须重新批准，不能复用旧版本的 grant。没有 `suspended`，回滚要么重新走审批，要么把旧授权误当成新版本的授权。

**等批准不是故障。** 版本在 `awaiting_grant` 期间，调谐循环不激活也不计失败，旧版本继续服务；超时后撤销本次提交，见 01 号文档。没有这条，升级会在管理员批准前被自动补偿掉。

## 5. 执行点

每个 Host 函数在执行前做五项检查，顺序固定，任一失败即拒绝。

1. 应用身份：调用来自哪个实例，实例是否属于该应用。
2. 包身份：运行时上报的 `app_version` 与包摘要，必须与 grant 上绑定的值一致。同版本号换包不继承授权。
3. grant：存在未撤销、未过期的 grant，且范围覆盖本次资源。
4. 策略：设备级策略当前是否允许该类操作。
5. 配额：本次调用是否超过速率、并发、存储上限。

拒绝返回类型化错误，不返回通用失败：

```
denied_not_granted
denied_expired
denied_policy
denied_scope
denied_quota
denied_revoked
denied_package_mismatch
```

**审计分级。** 状态变更（批准、撤销、拒绝批准、安装、卸载）同步写 FULL 审计。逐次放行与拒绝不进 Host 调用的同步路径：拒绝按应用与错误码聚合并限流，放行只累计计数，由后台批量写 NORMAL。每次读取都同步 FULL 会把读取路径拖慢，也会加速 eMMC 磨损。01 号文档的控制库与数据分库是这条规则的前提。

## 6. 撤销的时效

撤销必须在下一次调用生效，不能等应用重启。

- `grant` 表带 `revoked_at`。
- app-manager 维护一个授权代次 `grant_generation`，撤销时 +1。
- 宿主在每次 Host 调用前比对本地缓存的代次，不一致则重新拉取授权快照。
- 目标：撤销到生效的 p99 ≤ 200ms。这个数字是设计目标，未实测。
- 撤销同时向应用投递 `grant.changed` 事件（见 08 号文档），让应用主动停止相关操作，而不是等下一次调用才发现。

## 7. 权限点与角色

应用安装时生成权限点，命名沿用现有规则：

```
app.<app-id>:read        # 查看该应用页面与状态
app.<app-id>:control     # 启停该应用
app.<app-id>:configure   # 修改该应用参数
```

这三种是 Core 权限，写进 `permissions/catalog.yaml` 的运行期扩展，不走构建期展开。角色授予仍由管理员在角色管理里显式操作，不随应用安装自动授予。

参数与数据的权限边界：

- 读参数与读状态需要 `app.<id>:read`。
- 改参数需要 `app.<id>:configure`，与启停权分开，避免"能重启"被扩成"能改配置"。
- `secret` 字段只有写，没有读。管理员可以设置新值，但接口永不返回旧值，应用通过 Host ABI 在内存中读取。
- 应用自己的 KV 不需要额外权限点，命名空间隔离就是边界；跨应用读 KV 不存在对应的权限点，因为这条路径本身不开放。
- 界面沿用同一套权限：L0 详情与设置页需要 `app.<id>:read`，改参数需要 `configure`；L1 声明式页面的每个数据源单独校验；L2 webview 的每次 RPC 都同时校验用户会话、应用身份与应用命名空间，webview 不能借用户权限调用核心 API。

内置角色的默认建议：

| 角色 | 默认 |
| --- | --- |
| viewer | 无 |
| operator | `app.*:read` |
| engineer | `app.*:read`、`app.*:control`，可批准只读能力 |
| admin | 全部，可批准写能力 |

"可批准"也走权限点 `app.approve_read`、`app.approve_write`，不复用 `app.*:control`，避免启停权被扩成授权权。

## 8. 审计事件

必须记录的事件，字段至少包含 `app_id`、`app_version`、`capability`、`scope`、`actor`、`result`、`ts`。

```
app.install.requested
app.install.rejected          (原因码)
app.grant.pending
app.grant.approved
app.grant.denied
app.grant.revoked
app.start / app.stop / app.fault
app.cap.allowed               (摘要)
app.cap.denied                (含错误码，限流)
app.uninstall
```

审计落现有审计存储，不新建通道。

## 9. 拒绝路径的界面

- 应用详情页显示"已申请但未批准"的能力，以及申请时间。
- 启动按钮在存在 pending 能力时禁用，提示"等待授权"。
- 运行时拒绝在应用日志里可见，管理员可在审计里看到原因码。
- 撤销后在应用页面显示"权限已撤销"，不静默失败。

## 10. 验收

1. 清单含通配符，安装被拒。
2. 未批准的只读能力使应用停在 pending，启动返回拒绝。
3. 管理员批准后启动成功，审计有批准人和包摘要。
4. 撤销后 200ms 内下一次读取返回 `denied_revoked`。
5. 读未授权点位返回 `denied_not_granted`，不返回空值。
6. 写能力未经双人复核，批准被拒。
7. 同一应用重复批准不产生重复 grant。
8. `operator` 无法批准任何能力，`engineer` 无法批准写能力。
9. 拒绝日志按应用限流，1 秒内同错误码不超过 N 条。
10. 权限点在应用卸载后失效，旧 token 不能继续调用。
11. 升级到新版本后，旧版本的 grant 不生效，必须重新批准。
12. 用同一版本号替换包内容后启动，返回 `denied_package_mismatch`。
13. 回滚到旧版本时，只有仍有效且绑定该版本的 grant 恢复，其余保持撤销。

## 11. 未决

- `auto_grant_read` 是否应该默认开启。现场便利与安全默认值需要决策。
- 授权快照的存储形式与大小，是否复用注册表快照。
- 双人复核在离线设备上如何落，现有服务是否可离线。
- 应用权限点是否允许被自定义角色批量授予，还是必须逐个应用批准。
