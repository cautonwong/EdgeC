# 02 授权模型：声明、批准、执行、撤销

状态：第二轮修订（2026-11-09/10），待复审。未实现。

## 1. 结论先行

清单里的 `capabilities` 是**申请**，不是授权。授权来自三条同时成立：管理员批准、宿主策略允许、运行时逐次校验通过。任何一条不成立，调用被拒绝并留审计。

"能力即权限"把申请当成授权，是本设计明确否决的简化。声明与授权必须分开，见下一节。

### 威胁模型

按 STRIDE 对五个边界各看一遍，每一项都要有对应控制，不能只写"由权限系统保证"。

| 威胁 | 边界 | 具体场景 | 控制 |
| --- | --- | --- | --- |
| 仿冒 | 包 | 冒充官方应用 | 签名覆盖整个 payload；grant 绑定 `(app_id, capability, scope)` |
| 篡改 | 包 / 清单 | 安装后替换文件 | 加载前重新校验摘要；摘要不符拒绝启动 |
| 抵赖 | 批准 | 管理员否认批过写权限 | 审计记录批准人、时间、范围、工单 |
| 信息泄露 | 点位 | 应用读未授权点位 | 逐次校验；默认拒绝；无环境授权 |
| 拒绝服务 | 运行时 | 死循环、内存炸弹、调用风暴 | 看门狗、配额、Host 调用预算、导入白名单 |
| 提权 | 授权 | 用启停权换取批准权；通配符扩大范围 | 批准权与启停权分离；禁止通配；禁止自批 |
| 重放 | 下行 | 重放旧的控制命令 | 命令带时间戳与序列号；网关侧幂等键 |
| 供应链 | 包 | 降级到有漏洞的旧版本 | 版本只增不减；降级需显式操作并审计 |

"混淆代理人"是这里最容易被忽略的一项。应用不能把自己的权限借给另一个应用，也不能让宿主替它执行未授权的操作。Host ABI 每次调用都带实例身份，宿主不做"调用方未声明但看起来合理"的推断。

### 管理员身份（2026-11-09 已选定）

**本机账号为准，云端可选。** 批准、撤销、审计的 actor 是设备本机账号，不是 Edge-Ops 云端账号；Edge-Ops 只做策略下发与车队审批，设备离线时本机链路必须完整。

- **首次开机 provisioning**：串口或签名 provisioning token 创建 `admin`，不预设默认口令。设备不依赖云端完成首次配置。
- **角色**：沿用现有五个名字（ANONYMOUS/OBSERVER/OPERATOR/ENGINEER/ADMIN），但权限判定重写，不复用 `console_rbac_is_command_allowed()` 的字符串匹配。
- **账号存储**：控制库表，口令用 Argon2id（内存 64MB、迭代 3、并行 1）加盐存储；不放明文、不放 `system_params`。
- **口令策略（2026-11-09 已定）**：至少 12 字符，不强制组合规则，拒绝常见弱口令表与含设备序列号的口令；连续 5 次失败锁 5 分钟，10 次锁 30 分钟，只锁账号不锁设备，锁定/解锁写审计；无邮件/短信找回，由另一名 admin 重置，唯一 admin 丢失时用串口 + provisioning token 重置（要求物理接触）；provisioning 临时口令只能首次登录，改密前不能执行管理命令。
- **`appctl` 认证**：设备账号登录，不用 OS uid 作为身份。UDS 0600，`SO_PEERCRED` 只决定能否连接（root 或 `edgeos` 组）；连接后先 `login`，产品进程验账号口令并建 5 分钟会话，每条命令带会话 id。root 不自动成为管理员，审计同时记 `os_uid` 与 `actor`。
- **审计**：状态变更（安装、批准、撤销、升级、卸载）写控制库审计表，`synchronous=FULL`；逐次放行与拒绝按 01 号文档分级，不阻塞读取路径。
- **Edge-Ops 边界（2026-11-09 已定）**：可以分发签名包（只传输，不签名、不改包）与下发由厂商根/运维密钥签名的设备策略；下发失败时保留上一版策略。**v1 不允许 Edge-Ops 远程批准 grant**——批准必须落到设备本机账号，远程运维人员登录设备 WebUI 或 `appctl` 完成，审计 `actor` 是人。Edge-Ops 可读设备状态、应用清单、审计摘要；不可读 `app_kv`、`app_secret`、应用历史。远程批量批准要等设备 enrollment、管理员身份联邦与远程审批令牌设计完再评审。

**策略文件（2026-11-09 已定）。** canonical JSON（JCS）+ 分离签名 `policy.sig`；字段 `policy_version`、`policy_seq`（单调）、`device_scope`（型号/序列号/分组）、`issued_at`、`expires_at`、`auto_grant_read`、`settings`。设备记 `last_policy_seq`，低于等于它的策略拒绝；`expires_at` 过期后回落到内置默认策略，不无限沿用。策略只能收紧或开启 `auto_grant_read` 白名单，不能新增清单外能力，不能自动批准 `tags.write`，违反即整份拒绝。应用顺序：验签 → 校验 scope/seq/expiry → 写控制库并 bump `policy_generation`；失败保留上一版并写审计。离线可用 U 盘导入，需 `app.trust.import` + 双人复核。

**为什么不用现有实现。** `console_rbac.h` 有 IEC 62443 风格的角色与双人规则声明，但实现是桩：`console_rbac_verify_two_man_rule()` 接受任意 6 位数字（不校验 TOTP），并有四个硬编码口令（`624430`、`SUPERVISOR_KEY_2026`、`ADMIN_CONFIRM_99`、`AUTH_APPROVED`）；`console_audit` 是 1024 条内存环，从未初始化。角色名可以沿用，代码不能复用。

## 2. 四层分离

| 层 | 由谁产生 | 存在哪里 | 能改变什么 |
| --- | --- | --- | --- |
| 申请 | 应用作者，写进 `app.yaml` | `app_version.manifest` | 只决定"能申请什么" |
| 批准 | 管理员，显式操作 | `grant` 表，绑定 `(app_id, capability, scope)` | 决定"实际给了什么" |
| 策略 | 设备所有者，设备级配置 | 策略文件，随固件或运维下发 | 决定"这类申请现在允不允许" |
| 执行 | 宿主，每次 Host 调用 | 运行时内存中的授权快照 | 决定"这一次放不放行" |

四层的顺序不能颠倒。批准不能绕过策略，执行不能绕过批准。

## 3. 能力模型

能力按资源类型分组，每个能力带范围。范围是必须的，不接受"申请全部"。

```yaml
capabilities:
  tags:
    read:  [U_A, U_B]        # 明确点位，不支持通配
    write: []
  alarms:
    raise: [power.voltage]   # 明确规则类型
  kv: {}
  schedule:
    jobs: []
  net:
    egress: []               # 默认空，即禁止
```

v1 只开放 `tags.read`（单点位）、`points.publish`（仅自身 `app.<id>.*` 命名空间）、`kv`、`log`。`tags.write`、`alarms.raise`、`net.egress` 在 P0 之后单独评审。

通配符只允许出现在宿主策略里，不允许出现在应用清单里。应用写 `U_*` 直接判为非法清单。范围里的点位名由产品 ACL 解析，不创建新的全局数字 TagID（ADR-0010）；注册表分配的槽位是设备内 infra 编号，不是公共身份，不出现在清单、UI 或北向协议里。

## 4. 批准流程

```
申请(manifest)
   │
   ├─ 静态检查：范围是否合法、是否含通配、是否属 v1 开放集、
   │      requires/contributes 与能力范围是否一致
   │      └ 不通过 → 拒绝安装，不产生 grant
   │
   └─ 全部能力 → grant 状态 pending，应用可安装但不可启动
          └ 管理员批准 → granted；拒绝 → denied，可卸载
```

**自动批准策略（2026-11-09 已定）。** 默认关闭；P0 固定关闭，所有 grant 经 `appctl grant` 显式批准以验证链路。长期策略：设备策略 `auto_grant_read: [publisher_key_fingerprint...]` 可对受信发布者自动批准 `tags.read` 与 `points.publish`（仅自身命名空间）；`tags.write`、`alarms.raise`、`net.egress` 永远不自动批准。自动 grant 记录 `actor=policy`、策略版本与指纹，和人工批准一样可查、可撤销，撤销后不因策略仍在而复活；首次安装显示"已按策略自动批准"，不静默。Edge-Ops 只能下发已签名的策略文件，不能临时放宽。

写能力不接受自动批准。批准写能力必须满足：

1. 操作者具备 `app.approve_write` 权限。
2. 触发**双人复核**。现有 `console_rbac_verify_two_man_rule()` 不能复用（见上节），必须重写为"两个不同的本机账号、各自可验证的凭据、5 分钟窗口、离线可用"。全文统一用"双人复核"，不再使用"二次确认"这类会与普通确认混淆的说法。
3. 记录工单号或原因，为空拒绝。
4. 设备不处于"调试窗口期"以外的宽松模式。

**离线设备的双人复核。** 现场经常没有网络，不能依赖远程审批。规则是：两名不同的设备账号都具备 `app.approve_write`，在同一台设备上分别登录（各自独立会话），两次批准间隔不超过 5 分钟，且发起人不能是复核人。同一个账号开两个会话不算两个人。两次凭据都通过本地校验后写入一条审批记录，记录两个账号与时间。没有网络也能完成，但必须有两个人。

**撤销的耐久性。** 授权撤销与审计写入使用 `synchronous=FULL`（详见 01 号文档），落盘后才返回成功。否则掉电会把已撤销的能力复活，这比丢一条安装记录严重得多。

### 权限生命周期

参照 Android 与 iOS 的做法，权限不是一次性永久授予，而是有生命周期和可见状态。网关场景的差别是没有应用运行时的用户弹窗，所以把"运行时征得同意"换成"安装与批准时显式确认，运行期可查可撤"。

| 类型 | 例子 | 授予方式 | 有效期 |
| --- | --- | --- | --- |
| 普通 | 读单点位、写命名空间 KV | 管理员一次批准 | 长期，可撤销 |
| 敏感 | 写点位、发告警 | 管理员 + 双人复核 | 长期，可撤销，需工单 |
| 一次性 | 读取一次诊断快照 | 批准后首次调用即失效 | 单次 |
| 限时 | 调试窗口内的写操作 | 管理员批准 | 到期自动失效 |

- 敏感能力必须可单独撤销，不能只能整个应用卸载。
- 应用页面显示已授予、待批准、已暂停、已撤销四种状态，以及每项的批准人与时间。
- 撤销立即生效，下一次调用返回 `denied_revoked`，并在应用日志中可见。
- 不允许"一键全授权"。批量批准只能逐个勾选，避免管理员在不看范围的情况下放过全部。
- 授权不能复制给另一个应用。克隆应用时授权全部重新走批准流程。

**继承与暂停。** grant 按 `(app_id, capability, scope)` 存在，不绑定版本或包摘要；包摘要只进审计。升级时：不变或收窄的能力自动继承；新增或扩大 scope 进 `awaiting_grant`，升级可以完成，但新能力在批准前不可用。`tags.write`、`alarms.raise`、`net.egress` 在 ABI 主版本变化或发布者密钥轮换时重新批准，普通小版本不重批。已撤销的 grant 不因升级复活。点位改名或 `contract_version` 变化时，旧 scope 对应项收窄或失效，新增点必须重新批准，不能映射到同名新点。回滚时旧版本 grant 从 `suspended` 恢复，新版本继承的 grant 失效。

**等批准不是故障。** 版本在 `awaiting_grant` 期间，调谐循环不激活也不计失败，旧版本继续服务；超时后撤销本次提交，见 01 号文档。没有这条，升级会在管理员批准前被自动补偿掉。

## 5. 执行点

每个 Host 函数在执行前做五项检查，顺序固定，任一失败即拒绝。

1. 应用身份：调用来自哪个实例，实例是否属于该应用。
2. 包身份：运行时上报的 `app_id` 与 `publisher_id` 必须与安装记录一致；同版本号换包由版本与包摘要的防回滚规则拒绝，不靠 grant 绑定。
3. grant：存在未撤销、未过期的 grant，且范围覆盖本次资源。
4. **句柄权限**：`read` 句柄不能 publish，`publish` 句柄不能 read/subscribe；越权返回 `DENIED_SCOPE`。
5. 策略：设备级策略当前是否允许该类操作。
6. 配额：本次调用是否超过速率、并发、存储上限。

拒绝返回类型化错误，不返回通用失败：

```
denied_not_granted
denied_expired
denied_policy
denied_scope
denied_quota
denied_revoked
denied_package_mismatch
```

**审计分级。** 状态变更（批准、撤销、拒绝批准、安装、卸载）同步写 FULL 审计。逐次放行与拒绝不进 Host 调用的同步路径：拒绝按应用与错误码聚合并限流，放行只累计计数，由后台批量写 NORMAL。每次读取都同步 FULL 会把读取路径拖慢，也会加速 eMMC 磨损。01 号文档的控制库与数据分库是这条规则的前提。

## 6. 撤销的时效

撤销必须在下一次调用生效，不能等应用重启。

- `grant` 表带 `revoked_at`。
- app-manager 维护一个授权代次 `grant_generation`，撤销时 +1。
- 宿主在每次 Host 调用前比对本地缓存的代次，不一致则重新拉取授权快照。
- 目标：撤销到生效的 p99 ≤ 200ms。这个数字是设计目标，未实测。
- 撤销同时向应用投递 `grant.changed` 事件（见 08 号文档），让应用主动停止相关操作，而不是等下一次调用才发现。

## 7. 权限点与角色

应用安装时生成权限点，命名沿用现有规则：

```
app.<app-id>:read        # 查看该应用页面与状态
app.<app-id>:control     # 启停该应用
app.<app-id>:configure   # 修改该应用参数
```

另有平台级权限：`app.approve_read`、`app.approve_write`（批准能力）与 `app.trust.import`（导入第三方信任根），只授给 `engineer` / `admin`，并与 `app.*:control` 分开，避免启停权被扩成授权权。

这三种是 Core 权限，写进注册表并由快照下发。核心权限仍在 `permissions/catalog.yaml` 构建期展开；应用权限点来自注册表快照，经 `/api/v1/ui/bootstrap` 的 `app_permissions` 下发给 SPA，运行时查询。两者合并成一个 `permission_source` 接口，避免两套判定。角色授予仍由管理员在角色管理里显式操作，不随应用安装自动授予。

**两层分开（2026-11-09 已定）。** 角色对应用的访问权（`:read`/`:control`/`:configure`）可以按应用批量授予，审计逐条记录 app_id；能力 grant（应用能碰什么）永远逐个能力+范围批准，禁止"一键全授权"。自定义角色拿到 `:control` 不等于能替应用批准 `tags.write`，后者仍要 `app.approve_write` 且走双人复核。应用卸载后角色权限自动失效，不留悬空权限。

参数与数据的权限边界：

- 读参数与读状态需要 `app.<id>:read`。
- 改参数需要 `app.<id>:configure`，与启停权分开，避免"能重启"被扩成"能改配置"。
- `secret` 字段只有写，没有读。管理员可以设置新值，但接口永不返回旧值，应用通过 Host ABI 在内存中读取。密文用设备主密钥加密，主密钥不导出；备份恢复到另一台设备时标记"需重新录入"。详见 06 号文档。
- 应用自己的 KV 不需要额外权限点，命名空间隔离就是边界；跨应用读 KV 不存在对应的权限点，因为这条路径本身不开放。
- 界面沿用同一套权限：L0 详情与设置页需要 `app.<id>:read`，改参数需要 `configure`；L1 声明式页面的每个数据源单独校验；L2 webview 的每次 RPC 都同时校验用户会话、应用身份与应用命名空间，webview 不能借用户权限调用核心 API。

内置角色的默认建议：

| 角色 | 默认 |
| --- | --- |
| viewer | 无 |
| operator | `app.*:read` |
| engineer | `app.*:read`、`app.*:control`，可批准只读能力 |
| admin | 全部，可批准写能力 |

"可批准"也走权限点 `app.approve_read`、`app.approve_write`，不复用 `app.*:control`，避免启停权被扩成授权权。

## 8. 审计事件

必须记录的事件，字段至少包含 `app_id`、`app_version`、`capability`、`scope`、`actor`、`source`（`appctl` / `ui`）、`result`、`ts`。

```
app.install.requested
app.install.rejected          (原因码)
app.grant.pending
app.grant.approved
app.grant.denied
app.grant.revoked
app.start / app.stop / app.fault
app.cap.allowed               (摘要)
app.cap.denied                (含错误码，限流)
app.uninstall
```

审计落**控制库审计表**（状态变更 `synchronous=FULL`）。现有 `console_audit` 是 1024 条内存环、从未初始化，只能作为字段格式参考，不能作为持久存储。

**保留与分级（2026-11-09 已定）。** 关键审计（安装、批准、撤销、卸载、信任根变更、双人复核）至少保留 5 年，不自动清理；高频审计（`app.cap.allowed` / `app.cap.denied` 等）保留 90 天，表上限 100MB，超了删最旧。审计只追加，数据库触发器拒绝 `UPDATE`/`DELETE`，清理任务用专用连接绕过；关键表满了告警，不静默删。支持按时间/应用导出 JSONL，导出动作本身写审计；Edge-Ops 只读摘要，不拉全量。审计与状态变更同事务 `synchronous=FULL`，宁可拒绝操作，不丢审计。

## 9. 拒绝路径的界面

- 应用详情页显示"已申请但未批准"的能力，以及申请时间。
- 启动按钮在存在 pending 能力时禁用，提示"等待授权"。
- 运行时拒绝在应用日志里可见，管理员可在审计里看到原因码。
- 撤销后在应用页面显示"权限已撤销"，不静默失败。

## 10. 验收

1. 清单含通配符，安装被拒。
2. 未批准的只读能力使应用停在 pending，启动返回拒绝。
3. 管理员批准后启动成功，审计有批准人和包摘要。
4. 撤销后 200ms 内下一次读取返回 `denied_revoked`。
5. 读未授权点位返回 `denied_not_granted`，不返回空值。
6. 写能力未经双人复核，批准被拒。
7. 同一应用重复批准不产生重复 grant。
8. `operator` 无法批准任何能力，`engineer` 无法批准写能力。
9. 拒绝日志按应用限流，1 秒内同错误码不超过 N 条。
10. 权限点在应用卸载后失效，旧 token 不能继续调用。
11. 升级后不变或收窄的 grant 自动继承，新增或扩大的能力保持 pending，已撤销的 grant 不复活。
12. 用同一版本号替换包内容后启动，返回 `denied_package_mismatch`。
13. 回滚到旧版本时，旧版本 `suspended` 的 grant 恢复；新版本继承的 grant 失效，其余保持撤销。
