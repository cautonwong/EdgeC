# 后装应用平台设计：声明式贡献 + 受限运行时

状态：提案，待评审。**这是方向性架构，不是可直接冻结的实施基线。**
范围：后装应用（C/C++、Rust、Go、WASM、未来 Python）如何与 WebUI、北向、告警、存储、调度协作。
现状基线：DataHub、北向端口、构建期 Registry 是当前实现，可作为复用起点，不视为不可修改约束。

实施门槛：本文及 `app-platform/01` 至 `05` 均完成人工评审并冻结后，才可开始 P0；P0 的验收和退出条件全部满足后，才可进入 P1。若目标设计需要偏离已接受的 ADR，须在实施前提交对应的 ADR 修订提案，说明代码改动、迁移和验收；当前 ADR 是现状决策，不能被本提案静默覆盖。

## 1. 问题与目标

现在每接一类新东西，都要在多个子系统各改一处。装一个电压越限应用，WebUI 要加页面，北向要加点位映射，告警要加规则，存储要加表。应用数 M 乘子系统数 N，工作量是 N×M，每加一次还要重新发版和验收。

目标是把集成工作量从 N×M 降到 N+M。应用只写一份声明清单和一段逻辑；子系统只实现一次"按贡献类型消费"，之后不认识任何具体应用。

这不是安全目标。降低集成成本和安全保证是两件事，本文件分开写。

## 2. 可信度边界

本文每一条结论标注三种状态之一，评审时按状态决定能不能当依据。

| 状态 | 含义 | 本文中的例子 |
| --- | --- | --- |
| 已验证 | 在本机或仓库里跑过、量过 | C 与 Go 的 WASM 产物体积；现有 `edge_app_mgr`、北向端口、网关注册联邦的接口形状 |
| 设计目标 | 有明确机制，但没实现，也没测过失败路径 | 注册表事务与 saga 补偿、WASM 中断、sidecar 配额、跨组件恢复 |
| 未验证的假设 | 只有判断，没有证据 | Python 运行时的资源画像、并发语义能否跨运行时统一、组合兼容性可控 |

任何标为"设计目标"的条目，都不能当作已经解决的安全或一致性结论写进 P0 冻结条件。

**关键论断登记**。正文只在有机制和证据时使用肯定语气，这里把最容易误读的十条集中列出。

| 论断 | 状态 | 证据或缺口 |
| --- | --- | --- |
| 应用点位不引入全局数字 TagID | 设计目标 | 依赖 P0 选定产品 ACL 或 ADR 修订 |
| 注册表用 desired/published 分离，读者只见已发布代 | 设计目标 | 01 号文档，未实现 |
| generation 永不回退 | 设计目标 | 依赖启动时的 `max(库, 上报)` 规则 |
| 撤销授权掉电不复活 | 设计目标 | 依赖 FULL 同步连接，未测 |
| WASM 导入白名单在实例化前拒绝 | 设计目标 | 03 号文档，未实现 |
| B 档提供进程级安全隔离 | 未验证 | 依赖 uid、seccomp、namespace，目标板未测 |
| Go 标准运行时编 WASM 体积过大 | 已验证 | 本机实测，Go 1.25.5；体积只作参考，档位由 RSS、启动、RPC 决定 |
| Go 是否应走 sidecar | 设计目标 | 需 RSS、启动、RPC 三项实测 |
| Python 可作为正式运行时 | 未验证 | 资源画像完全未测 |
| 跨运行时行为一致 | 未验证 | 一致性矩阵只有 WASM 一列 |

## 3. 结论：方向成立，但要降低承诺

取 VS Code 的**声明式贡献点**，取 iPhone 的**签名包、能力声明、沙箱、生命周期**。不取 VS Code 让扩展在特权进程跑任意 JS，也不取 iPhone 让每个应用替换整个界面。

应用可以有界面，但只能在平台给的面上：自动生成的详情与设置页、声明式页面与卡片、沙箱 webview。外壳、导航、登录、权限管理始终归平台。

但"声明式贡献 + 受限运行时"只解决集成成本。它不会自动带来权限正确、故障隔离或跨组件一致性。下面每一节都要给出机制，而不是口号。

## 4. 现有可复用的支点

- `modules/edge_mgmt/include/edgeos/edge_app_mgr.h` 已有应用清单、状态机、安装/启动/停止/卸载/开机恢复。
- `modules/edge_io/include/edge_north_plane.h` 的北向端口已有 `peek`、`name`、`resolve_name`、`accept`、`on_downlink`，北向编排不认识产品点位模型。
- `go/cmd/edge-gateway/main.go` 已有服务注册：服务上报 `Tags` 与 `UIConfigs`，网关融合后由 `/api/v1/ui/bootstrap` 下发。这是贡献注册表的雏形，但当前没有类型、版本和校验。
- `web/core/src/modules` 的页面、`modules.manifest.yaml` 的构建期注册表、`permissions/catalog.yaml` 的权限目录，已经定义了页面、权限、能力怎么被表达。
- `modules/edge_stream/src/wasm_runtime` 已有 WAMR 宿主与看门狗，但现有 ABI 是模块 `"env"` 加全局数字 TagID（见 `docs/wasm_micro_app_guide.md` 与 `examples/wasm/*`）。这套 ABI 与 ADR-0010 冲突，新平台不能沿用它，P0 必须先决定拒绝还是兼容。

要做的是把这个弱约定升级成有类型、有版本、有事务的注册表，而不是另起一套。

**与现有 ADR 的关系。** 本提案不能静默覆盖已接受的决策。

- **ADR-0010 废除全局数字 TagID**，点位由产品聚合根自治。因此应用点位不得注册新的全局 TagID；默认命名是 `app.<app-id>.<point-name>`，由产品层映射，应用宿主只经 Host ABI 与产品端口访问数据。
- **ADR-0011 把 DataHub 归 infra**，组件只能通过端口访问。应用宿主不得直接引用 `datahub.h`。
- **ADR-0007 使用 `synchronous=NORMAL`**，掉电可能丢失最近的已提交事务，但数据库保持一致。本文后续的恢复承诺必须与此一致，不得宣称"已确认提交必保留"。

**P0 必须选定的落地路径。** 应用点位目录只有两条路，P0 冻结前选一条，并写出受影响模块、迁移、回滚与验收：

1. 目录并入 DataHub。需要扩展端口、存储与重启恢复路径，并提交 ADR-0010/0011 的修订提案。
2. 目录留在应用注册表，由产品 ACL 映射。需要扩展产品适配器，把应用命名空间解析到既有产品点位，并定义实时访问与历史解析的边界。

无论选哪条，既有产品点位身份必须继续有效，`edge_app_mgr` 必须持久化绑定包身份的授权，UI 与北向必须按 generation 消费快照并能报告是否已收敛。

**两条路径都需要 ADR 修订。** 应用点位是产品静态点表之外的动态命名空间，这一条要在 ADR 修订里写清楚，否则与"点表静态、manifest 不进运行时"冲突。修订要覆盖三点：动态命名空间的存在、与产品静态点表的边界、解析发生在 infra 层。草案与产品点位剖面见 `app-platform/10-product-points.md`。

**跨进程的授权强制点。** app-host 与 sidecar 不在网关主进程里，`point_read` 必须跨进程。通道、身份令牌与最终授权判定见 `app-platform/11-process-topology.md`。在它定稿前，不实现 A 档的数据通道。

## 5. 目标架构

层间只有一条不变式：

> 子系统只认识贡献类型，不认识应用名。

```
┌──────────────────────────────────────────────────────────┐
│ L4 产品 ACL 与子系统适配器（按类型消费贡献）               │
│  WebUI 渲染 / 北向映射 / 告警 / 存储 / 调度                │
└───────────────▲──────────────────────────────────────────┘
                │ 只读：按 contribution type + generation 查询
┌───────────────┴──────────────────────────────────────────┐
│ L3 应用贡献注册表（类型、版本、快照、事务日志；app 命名空间）│
└───────────────▲──────────────────────────────────────────┘
                │ SQLite 事务、快照发布与 saga 补偿
┌───────────────┴──────────────────────────────────────────┐
│ L2 应用宿主与运行时适配                                   │
│  WASM 宿主进程 / 每应用 sidecar / 统一 Host ABI           │
└───────────────▲──────────────────────────────────────────┘
                │ 宿主函数：tag / alarm / kv / log
┌───────────────┴──────────────────────────────────────────┐
│ L1 平台服务：DataHub / 应用点位存储 / 事件总线 / SQLite 等 │
└──────────────────────────────────────────────────────────┘

网关主进程 ── 不加载任何应用代码
```

图中的 DataHub 标注表达当前实现。应用点位目录可以留在 L3，也可以通过经评审的接口扩展由 DataHub 承载；目标归属在 P0 设计基线中确定。

**产品 ACL** 指产品侧的点位访问层，负责把 `app.<app-id>.<point-name>` 解析到该产品自己的点位标识与权限范围。它不是新的全局命名空间，不创建全局数字 TagID（ADR-0010），也不让应用宿主直接接触 `datahub.h`（ADR-0011）。

## 6. 进程与隔离模型

"进程内 WASM"与"应用代码不在主进程"不能同时成立。本设计的"进程内"限定为"在专用的应用宿主进程内"。

修正后的模型是三层进程，隔离承诺逐层减弱并写明。

| 档位 | 适用语言 | 所在进程 | 保证 | 残余风险 |
| --- | --- | --- | --- | --- |
| A WASM 宿主进程 | C、C++、Rust、Zig、TinyGo | 一个专用 app-host 进程，内含 N 个 WASM 实例 | 实例间线性内存隔离；CPU 用 fuel/epoch 中断；单实例 trap 只停该实例 | app-host 进程本身崩溃或 OOM 会带走全部 WASM 应用；靠 supervisor 重启并重新激活 |
| B 每应用 sidecar | Go、Python、Node | 每应用一个进程 | 进程级隔离；崩溃、泄漏、死循环只影响自己 | 进程数上限与内存上限必须显式配置，否则会被慢启动应用吃光 |
| C 共享 sidecar | 无默认场景 | 同语言多应用共进程 | 均摊内存 | 重新引入共享故障，仅在内存极紧的设备上显式开启 |

三条规则。

1. **网关主进程永远不加载应用代码。** 这条没有例外。
2. **ABI 与传输解耦。** 同一个 Host 函数，WASM 宿主里是直接调用，sidecar 是 unix socket 上的 RPC。应用代码和生成绑定不感知差别。
3. **档位由宿主策略决定，不由开发者任选。** 清单分别声明 `language`、`execution_profile` 与 `runtime_engine`；宿主校验组合、版本和配额后决定是否准入。语言名称不得兼作运行时或隔离档位。

WASM 不等于完整沙箱，这一点要写进承诺里。线性内存隔离只保证应用读不到别的实例的内存。它不自动保证：

- CPU 被抢占：需要 fuel 计量或 epoch 中断，否则一个死循环就是一次拒绝服务。
- 系统调用受限：需要 WASI 能力裁剪，默认只给 clock 与 random，其余关闭。
- 宿主函数被滥用：每个 Host 函数都要做参数校验、能力校验、配额扣减。
- 故障被隔离：WASM trap 必须在实例级捕获，不能冒泡到宿主进程；宿主进程自身崩溃由 supervisor 兜底。
- 内存被真正限制：依赖运行时把 `heapKb` 映射为线性内存上限，并且宿主自己不为应用分配无界缓冲。

## 7. 能力与授权：声明不等于授权

"能力即权限"是错误简化。应用在清单里声明能力，只是**申请**。完整链路有五步，缺一步就不该放行。

1. **声明**：清单 `capabilities.tags.read: [U_A]` 表达"我要什么"；范围由产品 ACL 解析，不创建全局 TagID。
2. **批准**：安装时由管理员显式确认，并写入授权记录，至少绑定 `app_id`、`app_version`、签名包摘要、能力、范围、批准人和时间。升级版本不继承旧版本授权；回滚只能恢复仍有效且明确绑定旧版本的授权。默认不批准任何写能力。
3. **策略**：宿主策略叠加设备级限制，例如"当前处于调试窗口期，禁止新增写点位应用"，或"该应用签名者不在白名单"。
4. **运行时校验**：每次 Host 调用都校验调用实例、应用版本与包身份、授权范围和当前策略；越权返回 `denied` 并记审计。校验发生在运行时，不能只在安装时做一次。
5. **撤销与审计**：管理员可随时撤销某个能力，下一次调用立即生效；所有放行与拒绝都进现有审计日志。

所以"声明是唯一授权来源"这句话要改成"**声明是申请，授权来自管理员批准加宿主策略，运行时逐次校验**"。

P0 固定关闭只读自动授权，所有 P0 grant 都经 `appctl` 显式批准；更广泛的只读自动授权策略须在 P0 后单独决策。对写能力再加两条：写点位默认需要**双人复核**；对同一应用的写频率设上限，超限按故障策略处理。

## 8. 贡献注册表不是普通配置表

注册表影响应用贡献声明、权限目录、UI 路由、北向映射和历史数据。它负责应用命名空间内的点位身份与生命周期；产品 ACL、DataHub 端口和其他子系统按 generation 消费快照。应用点位可由产品 ACL 映射，也可由经 ADR 批准的 DataHub 扩展直接承载；P0 开始前必须选定实现路径。

给出一个可实现的模型，并明确它的边界。

**存储**：SQLite 中的应用版本、贡献、授权与事务记录以数据库为持久事实源。贡献记录至少包含 `app_id`、`app_version`、`type`、`payload`、`state`、`generation`、`txn_id`。状态转换在事务中更新，并记入 `txn` / `txn_step`；读路径使用不可变快照。该注册表不替代产品点位目录。

**安装事务与补偿**：步骤、状态机与恢复矩阵以 `app-platform/01-registry-transaction.md` 为唯一权威，本文不复述。三条不变式：

1. 提交只写 `desired_version`，读者不可见。
2. 健康检查通过后才写 `published_version`、推进 generation、发布快照，读者才可见。
3. generation 永不回退；补偿是前向提交，不删除历史记录。

**跨组件的一致性边界**：SQLite 事务只覆盖注册表本身，运行时启动不在数据库事务里，因此这是 saga，不是两阶段提交。原子 rename 只保证单个消费者读到完整快照，不保证所有消费者同时切换；消费者须暴露 generation，跨组件联动在确认收敛前不得对外宣称完成。补偿动作要幂等，失败要能重放。

**掉电恢复要求**：数据库是持久事实源；`/run` 是 tmpfs，快照与指针重启即丢，从数据库重建，不需要 fsync 目录。发布只需保证 rename 的原子性。SQLite 使用 ADR-0007 的 `synchronous=NORMAL`，掉电可能丢失最近的已提交事务，因此只承诺"恢复为完整的提交前或完整的提交后状态，不出现混代"，不承诺"已确认提交必保留"；撤销与状态审计例外，走 FULL。

**卸载**：把该 `app_id` 的全部贡献标 `state=retired`，由选定的应用目录或产品历史存储保留必要的解析映射，北向停止上送，UI 路由移除，权限点标记失效。运行时消费者不得再把退役点位作为活动数据源；历史查询仍能解析名称。不能直接删除历史映射，否则历史曲线会断。

**升级**：新版本先成为 `desired_version`，健康后成为 `published_version`；旧版本保留一个版本后标 `retired`。回滚是把两个指针指回旧版本并前向推进一代，不删数据。

**稳态调谐。** 安装事务只覆盖"变更那一刻"。除此之外还需要一个 level-triggered 的调谐循环，周期性地把期望状态与观测状态对齐：该跑没跑就启动，不该跑却在跑就停止，版本不符就切换，授权已撤销就拒绝。没有它，一次丢失的事件或一次手工操作就会让系统停在中间态。细节见 `app-platform/01-registry-transaction.md`。

**消费者收敛。** 快照保证单个读者读到完整的一代，不保证所有读者都读到了。消费者在内存中保存 `applied_generation` 并向注册表心跳上报，重启后整份重放；安装完成的定义是全部消费者追平目标代，而不是快照文件已替换。

**事件模型。** 不造通用事件总线。数据面用 DataHub 的订阅与死区，控制面用 generation 与消费者偏移，浏览器面用现有 `/api/v1/ws` 主题与缺号 resync，宿主面用每应用有界队列；另加一条只允许平台发、应用收的小通道，六个类型：设置变化、授权变化、上游可用或不可用、代次变化、即将停止。应用之间不发事件，只发点位。iOS 与 VS Code 都没有通用跨应用总线，理由和语义见 `app-platform/08-events.md`。

**应用参数与数据。** 参数在清单里用 schema 声明，默认值在安装时写入 `app_settings`，密钥进单独的表且只写不读，界面由 schema 生成。运行时数据进按应用隔离的 `app_kv`，不进包目录，也不进全局 `system_params`。这些是私有数据，跨应用不可见。细节见 `app-platform/06-data-and-configuration.md`。

**后装应用怎么拿已有数据。** 只有一条路：发布方把数据以点位发布，消费方申请读取授权。DataHub 保留最新值，新装应用授权后立刻拿到当前值；历史值要求发布方声明保留且消费方获批。发布方没装时，消费方以降级状态启动，不阻塞安装。发布方没发布这个点位时，消费方拿不到，这是封装，解决办法是发布方发新版本，而不是装 B 去改 A。

上述机制是设计目标，没有实现，也没有故障注入测试。P0 不应把它当作已解决。事务细则还须与本节统一 generation 单调性、激活可见性、授权绑定及重启重建规则。

## 9. 贡献类型：点位与三档界面

贡献类型不一次全开。点位先行，界面分三档逐步开启，其余按触发条件延后。

| 类型 | 阶段 | 风险 | 说明 |
| --- | --- | --- | --- |
| `telemetry.points` | P0 纵切；通过后纳入只读候选 | 低 | 应用命名空间声明；由产品 ACL 映射或经评审的 DataHub 扩展承载 |
| `ui.detail` / `ui.settings` | P1 自动生成 | 低 | 详情页、设置表单，由清单 schema 生成，不写界面代码 |
| `ui.pages` / `ui.widgets` | P1 单独评审 | 中 | 声明式布局，白名单组件，服务端解析数据引用 |
| `ui.webview` | P2 | 高 | 沙箱 iframe，签名静态包，窄 RPC，无网络无同源 |
| `northbound.metrics` | 延后 | 中 | 等点位注册表事务模型验证后再评审 |
| `alarm.rules` | 延后 | 高 | 需要受限表达式语言，见第 10 节 |
| `schedule.jobs` | 延后 | 中 | 与任务调度的抢占语义未定 |
| `protocol.handlers` | 不纳入计划 | 很高 | 本质是可执行扩展点，v1 不作为贡献类型 |

本文中的 **P0** 是验证事务、授权和运行时隔离的最小纵切。P0 通过不会自动启用任何界面；界面分为 U0 生成、U1 声明、U2 沙箱三档，与项目阶段 P0/P1/P2 区分。U0 与 U1 需要参数模型跑通，U2 需要 CSP、opaque origin、RPC 白名单三项安全测试通过。细节见 `app-platform/07-ui-surfaces.md`。

## 10. 每种贡献的安全语义

"都是数据不是代码"这句话只对一部分类型成立，必须逐类说清。

**`telemetry.points`**：纯元数据。风险在命名冲突与配额。用 `app.<app-id>.` 前缀限定应用内名称，注册时校验唯一性和配额。点位可通过产品 ACL 映射到现有产品测点，也可由批准后的 DataHub/端口扩展承载应用派生值；选定路径必须保留现有产品点位兼容，并定义卸载后的历史解析与实时访问撤销。

**`ui.pages` / `ui.widgets`**：不是任意前端。布局只允许封闭组件集合，数据引用只能是点位标识或注册表内的查询名，由服务端解析成值后再下发。应用不能提供 URL、不能内联脚本、不能指定 CSS。渲染器对每个页面和每个数据源都做一次权限校验，防止"页面可见但数据越权"。

**`ui.webview`**：应用可以有自定义界面，但跑在 opaque origin 的 iframe 里，不加 `allow-same-origin`，CSP 禁止外联，只能通过白名单 postMessage 读取自己的数据。它不能读平台 Cookie、不能调核心 API、不能访问别的应用。入口在应用详情页内，不替换外壳。这是 VS Code webview 的对应物，不是 iPhone 的整页替换。

**`alarm.rules`**：不能是自由表达式。v1 若要做，只做**预置规则类型加参数**，例如 `threshold`、`rate_of_change`、`deadband`，由告警引擎解释，不引入表达式求值器。若确实需要表达式，必须选一个可静态分析、可设执行上限的子集，并给出深度、节点数、执行时间三重上限。在此之前不做。

**`protocol.handlers`**：不作为贡献类型。它要么是声明式帧映射（字段偏移到点位），由现有编解码器消费；要么就是一个需要驱动能力的运行时应用，走完整的能力审批与隔离。不允许应用注册 C 回调。

**`northbound.metrics` / `schedule.jobs`**：等前两类跑通后再评估。

## 11. 运行时一致性契约

"同一套 conformance 测试"是目标，不是自动成立的保证。四个运行时在中断、并发、时间、内存计量和进程退出上的机制根本不同，所以契约要写成**可观测行为一致，机制允许不同，差异显式登记**。

| 维度 | WASM 宿主 | QuickJS | Go / Python sidecar | 契约 |
| --- | --- | --- | --- | --- |
| 中断 | fuel 或 epoch 中断 | 解释器中断标志 | 宿主发信号，超时后 SIGKILL | 超时上限内必须停止；抢占延迟登记为各运行时属性 |
| 并发 | 默认单线程实例，v1 不开线程 | 单线程 | 语言自身并发，但 Host 调用按应用串行化 | 同一应用同一时刻只有一个 Host 调用在执行 |
| 时间 | 只能取宿主 `now_ms` | 同左 | 同左，禁用本地时钟 | 跨运行时时间源唯一 |
| 内存计量 | 线性内存上限 | 堆分配器计量 | cgroup 或 RLIMIT_AS | 超限触发故障策略，不静默继续 |
| 错误 | Host 错误映射为返回码 | 同左 | RPC 错误码 | 不跨边界抛原生异常 |
| 退出 | 实例 trap 或主动 stop | 运行时 stop | 进程退出 | 统一映射为 `faulted` 或 `stopped` |

v1 的一致性测试只覆盖 WASM 宿主。QuickJS 和 sidecar 的契约在各自接入时用同一套用例验证，结果填入这张表。没有填完之前，不对外承诺"跨运行时一致"。

## 12. 语言支持：C/C++、Rust、Go、Python

目标是每种语言都能写后装应用，但落地路径不同，不能一句"统一 SDK"带过。

**契约只有一份。** 用 WIT 定义 Host ABI，C/C++/Rust 用 `wit-bindgen` 生成绑定，Go 用同一份 IDL 生成 RPC 客户端，Python 用 `componentize-py` 或生成 sidecar 客户端。绑定是生成物，不进人工修改；WIT 的语义化版本就是清单里的 `sdk`。

**现有 ABI 不能沿用。** 仓库现在的 WASM 微应用用模块 `"env"` 加全局数字 TagID，`docs/wasm_micro_app_guide.md` 与 `examples/wasm/*` 都是这个写法。它与 ADR-0010 冲突。新平台的 ABI 是 `abi: 1`，旧模块要么被拒绝，要么走一个独立的兼容层，二者在 P0 前必须选定。旧指南要同步标注 legacy，否则新人会照着写装不进新平台的应用。

**C / C++**：第一类公民，走 A 档。用 clang `--target=wasm32` 或 WASI SDK 构建。C++ 必须关闭异常与 RTTI（`-fno-exceptions -fno-rtti`），否则产物和运行时开销都会膨胀；标准库只用头文件子集或 libc++ 的裁剪构建。最小应用实测 281 字节（C，`-nostdlib -O2`）。C++ 的实际体积尚未测量。仓库现有指南也推荐 C/C++ 与 TinyGo，理由是产物小、无 GC 停顿，与本机实测一致。

**Rust**：走 A 档，`wasm32-wasip1` 或 `wasm32-unknown-unknown`，`panic=abort`，`opt-level=z`。本机未安装该 target，体积未测。

**Go**：走 B 档 sidecar，用原生 Go 构建，不编 WASM。实测一个最小 Go 应用编成 wasip1 是 1,642,824 字节，剥符号后 gzip 仍有 492,130 字节，多出来的是一整份 GC 与调度器。同一逻辑的 C 产物是 281 字节，差约 5,800 倍。Go 的 SDK 是一个从同一份 IDL 生成的 RPC 客户端包，不是手写实现。

**Python**：走 B 档 sidecar，MicroPython 或 CPython 视内存预算。产物体积、启动时间、GIL 与 Host 调用的串行化行为都未实测。在测出来之前，不把它列进 v1 支持范围。

**JS**：QuickJS，A 档或 B 档待定。

**构建配方要进 CI。** 每种语言的示例应用都要在 CI 里构建并跑同一套 conformance 用例，否则"支持某语言"只是一句声明。

## 13. 兼容性：承认组合问题

应用版本、宿主版本、SDK 版本、贡献类型版本、权限模型版本、运行时版本叠加，确实是组合爆炸。不假装能全测。

做法是收敛维度并抽样。

- 与 03 号细则统一：宿主公布 `platform = (host, abi, contribSchema, permModel)`；应用清单声明 `minHost`、`sdk`、`language`、`execution_profile` 与 `runtime_engine`。SDK 与 ABI 是独立版本对象，按兼容矩阵校验，不得假定二者同号；运行时引擎及版本由宿主公布并参与准入检查。
- 支持策略是 **N-1**：宿主支持当前与上一个 SDK 主版本，更早的拒绝安装并给出升级提示。
- 安装时做静态兼容检查，运行时做一次握手校验，两者都失败即拒绝。
- 发布时跑一个**抽样矩阵**：每个运行时的最新两版 SDK × 当前宿主 × 当前与上一贡献 schema，其余组合不承诺。抽样矩阵的结果要归档，未覆盖的组合明确标注"未验证"。
- 升级前做一次"贡献 schema 迁移演练"，即用旧版贡献数据在新宿主上加载一次，失败则不允许升级。

组合问题不能消除，只能把承诺范围写清楚。

## 14. 纵切计划：先证明最关键的假设

在扩展任何类型之前，只做一条最小纵切，跑通全生命周期。它的目的是证伪，不是演示。

**范围**

- 一个运行时：WASM，宿主先选一个（WAMR 或 wasmtime，按目标板的内存与构建复杂度二选一，选型标准写进 ADR）。目标板型号、系统镜像和运行时版本须在选型 ADR 中固定。
- 一种贡献：`telemetry.points`，只读。
- 最小能力：`tags.read` 单点位，`log`。无写、无告警、无 UI。
- 一个语言：C。C++ 与 Rust 在纵切通过后加入构建矩阵。

**必须跑通的路径**

1. 打包并签名一个只读应用。
2. 安装：签名、schema、SDK、配额校验通过；能力进入待批准状态。
3. 批准：管理员授予单点位只读；审计记录批准人。
4. 启动：WASM 实例经产品端口订阅一个已授权点位，日志可见；应用宿主不直接访问 DataHub。
5. 越权：尝试读未授权点位，返回 `denied` 并写审计。
6. 故障：死循环触发 fuel/epoch 中断，实例标记 `faulted`，宿主进程存活。
7. 超限：分配超过 `heapKb`，实例失败，宿主不受影响。
8. 崩溃：kill 掉 app-host 进程，supervisor 拉起，应用按开机恢复策略重新激活。
9. 升级：安装新版本，健康检查通过后切换，旧版本保留。
10. 回滚：新版本激活失败，回退到旧版本，贡献一致。
11. 卸载：应用贡献标 `retired`，产品侧历史查询仍能解析既有点位；P0 不涉及 UI 或北向展示。
12. 掉电：在提交与激活之间断电，重启后从持久注册表重建快照，恢复为完整旧代或完整新代，不留下混代贡献。

**验收标准**：以上是纵切的主干路径。完整验收项、命令与证据格式见 `app-platform/05-p0-vertical-slice.md`，以那份为唯一来源，本文不复述数量。每条都要有日志或测试作为证据；任何一条失败，先修机制，不扩范围。

只有这条纵切通过，第 9 节的贡献类型才逐个放开；第 11 节的一致性矩阵才逐个填；Python 与 Go 才进入正式支持列表。

## 15. 后续阶段（按触发条件，不按时间表）

- 纵切与参数模型通过后，先做 U0 自动详情与设置页，再评审 U1 声明式页面；U2 webview 等安全测试通过后开启。
- 注册表事务模型经过故障注入验证后，开 `northbound.metrics`。
- Go sidecar 的 RPC 延迟与进程数上限实测后，把 Go 列入正式支持。
- 告警规则确定受限语义后，开 `alarm.rules`。
- Python 资源画像测出来后，再决定是否支持。
- `protocol.handlers` 暂不规划。

**迁移与废弃**与上面并行，不能等到最后。旧 WASM 运行时、旧 `env` ABI、QuickJS 脚本引擎、已装应用与商店页面的处置见 `app-platform/09-migration.md`。盘点清单为空之前，不移除旧运行时。

## 16. 反例与取舍

**不做 VS Code 式特权扩展。** 应用在宿主主进程跑任意 JS，等于放弃隔离。

**不做 VS Code 式单扩展宿主。** 所有应用挤在一个进程，一个死循环拖垮全部。本文的 A 档仍是共享 app-host 进程，但用实例级中断与故障策略把影响限制在单实例，并明确登记了"宿主进程崩溃会带走全部 WASM 应用"这一残余风险。

**不手写多语言 SDK。** 用一份 WIT 生成绑定，避免语义漂移。

**不做 iPhone 式整页替换。** 每个应用一套前端并接管导航，WebUI 会碎成十个风格，权限与审计无法统一。允许的是平台定义的三种界面面：自动详情与设置、声明式页面、沙箱 webview。

**不做 OSGi。** 动态加载 C 共享库在嵌入式网关上体积与 ABI 稳定性都不划算。

**不默认每应用一个进程。** 几十个应用会吃光内存。只有需要原生能力的语言进 B 档，并有进程数上限与 LRU。

**不把注册表做成可执行钩子。** 贡献是数据，不是回调。

**不把"声明"当"授权"。** 见第 7 节。

## 17. 未决与风险

- 注册表跨组件事务没有实现，也没有故障注入测试。掉电、激活失败、补偿失败三种路径都未验证。
- WASM 中断在目标运行时上的实际抢占延迟未测。用 fuel 还是 epoch 取决于运行时选型。
- app-host 进程是共享故障域。supervisor 重启能否在可接受时间内恢复全部应用，未测。
- Go sidecar 的 RPC 往返、冷启动、进程数上限对内存的影响，都未测。
- Python 的运行行为完全未验证，不列入 v1。
- 贡献 schema 的版本迁移没有演练过，升级路径可能比设想更脆。
- 权限点的生成与 `role-presets.yaml` 的构建期展开机制如何对齐，尚未定案。
- 组合兼容性只能抽样，未覆盖组合必须标注"未验证"，不能默认可用。
- `01` 至 `05` 号细则仍待评审；generation、激活可见性、授权版本绑定、SDK/ABI/运行时字段、应用点位承载路径及 P0 范围必须先与本文对齐。
- 快照消费者是否需要提交确认、SQLite 同步级别和目标板掉电注入条件尚未定案；在形成可复现证据前，不对外承诺跨组件原子性或提交耐久性。
