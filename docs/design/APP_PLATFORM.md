# 后装应用平台设计：声明式贡献 + 受限运行时

状态：提案，待评审。**这是方向性架构，不是可直接冻结的实施基线。**
范围：后装应用（C/C++、Rust、Go、WASM、未来 Python）如何与 WebUI、北向、告警、存储、调度协作。
不改变：现有 DataHub、北向端口、构建期 Registry 的既有权衡。

## 1. 问题与目标

现在每接一类新东西，都要在多个子系统各改一处。装一个电压越限应用，WebUI 要加页面，北向要加点位映射，告警要加规则，存储要加表。应用数 M 乘子系统数 N，工作量是 N×M，每加一次还要重新发版和验收。

目标是把集成工作量从 N×M 降到 N+M。应用只写一份声明清单和一段逻辑；子系统只实现一次"按贡献类型消费"，之后不认识任何具体应用。

这不是安全目标。降低集成成本和安全保证是两件事，本文件分开写。

## 2. 可信度边界

本文每一条结论标注三种状态之一，评审时按状态决定能不能当依据。

| 状态 | 含义 | 本文中的例子 |
| --- | --- | --- |
| 已验证 | 在本机或仓库里跑过、量过 | C 与 Go 的 WASM 产物体积；现有 `edge_app_mgr`、北向端口、网关注册联邦的接口形状 |
| 设计目标 | 有明确机制，但没实现，也没测过失败路径 | 注册表两阶段提交、WASM 中断、sidecar 配额、跨组件回滚 |
| 未验证的假设 | 只有判断，没有证据 | Python 运行时的资源画像、并发语义能否跨运行时统一、组合兼容性可控 |

任何标为"设计目标"的条目，都不能当作已经解决的安全或一致性结论写进 P0 冻结条件。

## 3. 结论：方向成立，但要降低承诺

取 VS Code 的**声明式贡献点**，取 iPhone 的**签名包、能力声明、沙箱、生命周期**。不取 VS Code 让扩展在特权进程跑任意 JS，也不取 iPhone 每个应用自带一套 UI。

但"声明式贡献 + 受限运行时"只解决集成成本。它不会自动带来权限正确、故障隔离或跨组件一致性。下面每一节都要给出机制，而不是口号。

## 4. 现有可复用的支点

- `modules/edge_mgmt/include/edgeos/edge_app_mgr.h` 已有应用清单、状态机、安装/启动/停止/卸载/开机恢复。
- `modules/edge_io/include/edge_north_plane.h` 的北向端口已有 `peek`、`name`、`resolve_name`、`accept`、`on_downlink`，北向编排不认识产品点位模型。
- `go/cmd/edge-gateway/main.go` 已有服务注册：服务上报 `Tags` 与 `UIConfigs`，网关融合后由 `/api/v1/ui/bootstrap` 下发。这是贡献注册表的雏形，但当前没有类型、版本和校验。
- `web/core/src/modules` 的页面、`modules.manifest.yaml` 的构建期注册表、`permissions/catalog.yaml` 的权限目录，已经定义了页面、权限、能力怎么被表达。

要做的是把这个弱约定升级成有类型、有版本、有事务的注册表，而不是另起一套。

## 5. 目标架构

层间只有一条不变式：

> 子系统只认识贡献类型，不认识应用名。

```
┌──────────────────────────────────────────────────────────┐
│ L4 子系统适配器（各实现一次，之后不再改）                 │
│  WebUI 渲染 / 北向映射 / 告警 / 存储 / 调度                │
└───────────────▲──────────────────────────────────────────┘
                │ 只读：按 contribution type + generation 查询
┌───────────────┴──────────────────────────────────────────┐
│ L3 贡献注册表（带版本、带快照、带事务日志）                │
└───────────────▲──────────────────────────────────────────┘
                │ 安装/升级/卸载时两阶段写入
┌───────────────┴──────────────────────────────────────────┐
│ L2 应用宿主与运行时适配                                   │
│  WASM 宿主进程 / 每应用 sidecar / 统一 Host ABI           │
└───────────────▲──────────────────────────────────────────┘
                │ 宿主函数：tag / alarm / kv / log
┌───────────────┴──────────────────────────────────────────┐
│ L1 内核：DataHub、事件总线、SQLite、审计、权限             │
└──────────────────────────────────────────────────────────┘

网关主进程 ── 不加载任何应用代码
```

## 6. 进程与隔离模型

先纠正上一版的自相矛盾。"进程内 WASM"和"应用代码不在主进程"不能同时成立，除非把"进程内"限定为"在专用的应用宿主进程内"。

修正后的模型是三层进程，隔离承诺逐层减弱并写明。

| 档位 | 适用语言 | 所在进程 | 保证 | 残余风险 |
| --- | --- | --- | --- | --- |
| A WASM 宿主进程 | C、C++、Rust、Zig、TinyGo | 一个专用 app-host 进程，内含 N 个 WASM 实例 | 实例间线性内存隔离；CPU 用 fuel/epoch 中断；单实例 trap 只停该实例 | app-host 进程本身崩溃或 OOM 会带走全部 WASM 应用；靠 supervisor 重启并重新激活 |
| B 每应用 sidecar | Go、Python、Node | 每应用一个进程 | 进程级隔离；崩溃、泄漏、死循环只影响自己 | 进程数上限与内存上限必须显式配置，否则会被慢启动应用吃光 |
| C 共享 sidecar | 无默认场景 | 同语言多应用共进程 | 均摊内存 | 重新引入共享故障，仅在内存极紧的设备上显式开启 |

三条规则。

1. **网关主进程永远不加载应用代码。** 这条没有例外。
2. **ABI 与传输解耦。** 同一个 Host 函数，WASM 宿主里是直接调用，sidecar 是 unix socket 上的 RPC。应用代码和生成绑定不感知差别。
3. **档位由运行时决定，不由开发者任选。** 清单 `runtime: c | cpp | rust | wasm | go | python | js` 映射到档位，宿主按配额做准入。

WASM 不等于完整沙箱，这一点要写进承诺里。线性内存隔离只保证应用读不到别的实例的内存。它不自动保证：

- CPU 被抢占：需要 fuel 计量或 epoch 中断，否则一个死循环就是一次拒绝服务。
- 系统调用受限：需要 WASI 能力裁剪，默认只给 clock 与 random，其余关闭。
- 宿主函数被滥用：每个 Host 函数都要做参数校验、能力校验、配额扣减。
- 故障被隔离：WASM trap 必须在实例级捕获，不能冒泡到宿主进程；宿主进程自身崩溃由 supervisor 兜底。
- 内存被真正限制：依赖运行时把 `heapKb` 映射为线性内存上限，并且宿主自己不为应用分配无界缓冲。

## 7. 能力与授权：声明不等于授权

上一版写"能力即权限"是错的。应用在清单里声明能力，只是**申请**。完整链路有五步，缺一步就不该放行。

1. **声明**：清单 `capabilities.tags.read: [U_A]` 表达"我要什么"。
2. **批准**：安装时由管理员显式确认，并写入 `app_grant` 表，记录批准人、时间、范围。默认不批准任何写能力。
3. **策略**：宿主策略叠加设备级限制，例如"当前处于调试窗口期，禁止新增写点位应用"，或"该应用签名者不在白名单"。
4. **运行时校验**：每次 Host 调用都查授权表与当前策略，越权返回 `denied` 并记审计。校验发生在运行时，不能只在安装时做一次。
5. **撤销与审计**：管理员可随时撤销某个能力，下一次调用立即生效；所有放行与拒绝都进现有审计日志。

所以"声明是唯一授权来源"这句话要改成"**声明是申请，授权来自管理员批准加宿主策略，运行时逐次校验**"。

对写能力，建议再加两条：写点位默认需要二次确认；对同一应用的写频率设上限，超限按故障策略处理。

## 8. 贡献注册表不是普通配置表

注册表同时影响 DataHub 点位表、北向映射、告警规则、权限目录、UI 路由和历史数据。这些状态必须一起变更，否则会出现"页面在、点位不在"或"点位在、权限没批"的中间态。

给出一个可实现的模型，并明确它的边界。

**存储**：一份 SQLite 表 `contributions`，字段包含 `app_id`、`app_version`、`type`、`payload`、`state`、`generation`、`txn_id`。读路径使用不可变快照，写路径只追加。

**两阶段**：

1. 预检：签名、schema、SDK 兼容、能力、配额、类型冲突，全部在内存里校验，失败不落盘。
2. 暂存：写入 `state=staged`，同一 `txn_id`。
3. 提交：在**一个 SQLite 事务**里把该 `txn_id` 的全部行改成 `state=active`，并把注册表 `generation` 加一。子系统读新 generation。
4. 激活：启动运行时，健康检查通过后写 `state=running`。
5. 失败：提交前失败则删除暂存；激活失败则用补偿动作把 `state` 回退到 `staged` 并回滚 generation。

**跨组件的一致性边界**：SQLite 事务只覆盖注册表本身。运行时启动不在数据库事务里，所以这里必须是 saga，不是两阶段提交。补偿动作要幂等，失败要能重放。应用激活到一半时设备掉电，重启后由日志重放决定是继续还是回滚。

**卸载**：把该 `app_id` 的全部贡献标 `state=retired`，点位保留为只读历史，北向停止上送，UI 路由移除，权限点标记失效。不能直接删除，否则历史曲线会断。

**升级**：新版本以新 `app_version` 暂存，两个版本贡献并存但只有新版本处于 `active`；健康检查通过后把旧版本标 `retired`，保留一个版本用于回滚。

上述机制是设计目标，没有实现，也没有故障注入测试。P0 不应把它当作已解决。

## 9. 贡献类型：v1 只开两个

上一版一次开六个，是把未验证的东西写成了计划。按风险排序，v1 只开只读点位与只读页面。

| 类型 | v1 | 风险 | 说明 |
| --- | --- | --- | --- |
| `telemetry.points` | 开 | 低 | 只读点位元数据，不写数据 |
| `ui.pages` | 开 | 中 | 声明式布局，白名单组件，服务端解析数据引用 |
| `northbound.metrics` | 缓 | 中 | 等点位注册表事务模型验证后再开 |
| `alarm.rules` | 缓 | 高 | 需要受限表达式语言，见第 10 节 |
| `schedule.jobs` | 缓 | 中 | 与任务调度的抢占语义未定 |
| `protocol.handlers` | 不开 | 很高 | 本质是可执行扩展点，v1 不作为贡献类型 |

## 10. 每种贡献的安全语义

"都是数据不是代码"这句话只对一部分类型成立，必须逐类说清。

**`telemetry.points`**：纯元数据。风险在命名冲突与配额。用 `app.<app-id>.` 前缀强制命名空间，注册时校验不冲突；应用卸载后点位保留只读。

**`ui.pages`**：不是任意前端。布局只允许封闭组件集合，数据引用只能是点位标识或注册表内的查询名，由服务端解析成值后再下发。应用不能提供 URL、不能内联脚本、不能指定 CSS。渲染器对每个页面和每个数据源都做一次权限校验，防止"页面可见但数据越权"。

**`alarm.rules`**：不能是自由表达式。v1 若要做，只做**预置规则类型加参数**，例如 `threshold`、`rate_of_change`、`deadband`，由告警引擎解释，不引入表达式求值器。若确实需要表达式，必须选一个可静态分析、可设执行上限的子集，并给出深度、节点数、执行时间三重上限。在此之前不做。

**`protocol.handlers`**：不作为贡献类型。它要么是声明式帧映射（字段偏移到点位），由现有编解码器消费；要么就是一个需要驱动能力的运行时应用，走完整的能力审批与隔离。不允许应用注册 C 回调。

**`northbound.metrics` / `schedule.jobs`**：等前两类跑通后再评估。

## 11. 运行时一致性契约

"同一套 conformance 测试"是目标，不是自动成立的保证。四个运行时在中断、并发、时间、内存计量和进程退出上的机制根本不同，所以契约要写成**可观测行为一致，机制允许不同，差异显式登记**。

| 维度 | WASM 宿主 | QuickJS | Go / Python sidecar | 契约 |
| --- | --- | --- | --- | --- |
| 中断 | fuel 或 epoch 中断 | 解释器中断标志 | 宿主发信号，超时后 SIGKILL | 超时上限内必须停止；抢占延迟登记为各运行时属性 |
| 并发 | 默认单线程实例，v1 不开线程 | 单线程 | 语言自身并发，但 Host 调用按应用串行化 | 同一应用同一时刻只有一个 Host 调用在执行 |
| 时间 | 只能取宿主 `now_ms` | 同左 | 同左，禁用本地时钟 | 跨运行时时间源唯一 |
| 内存计量 | 线性内存上限 | 堆分配器计量 | cgroup 或 RLIMIT_AS | 超限触发故障策略，不静默继续 |
| 错误 | Host 错误映射为返回码 | 同左 | RPC 错误码 | 不跨边界抛原生异常 |
| 退出 | 实例 trap 或主动 stop | 运行时 stop | 进程退出 | 统一映射为 `faulted` 或 `stopped` |

v1 的一致性测试只覆盖 WASM 宿主。QuickJS 和 sidecar 的契约在各自接入时用同一套用例验证，结果填入这张表。没有填完之前，不对外承诺"跨运行时一致"。

## 12. 语言支持：C/C++、Rust、Go、Python

目标是每种语言都能写后装应用，但落地路径不同，不能一句"统一 SDK"带过。

**契约只有一份。** 用 WIT 定义 Host ABI，C/C++/Rust 用 `wit-bindgen` 生成绑定，Go 用同一份 IDL 生成 RPC 客户端，Python 用 `componentize-py` 或生成 sidecar 客户端。绑定是生成物，不进人工修改；WIT 的语义化版本就是清单里的 `sdk`。

**C / C++**：第一类公民，走 A 档。用 clang `--target=wasm32` 或 WASI SDK 构建。C++ 必须关闭异常与 RTTI（`-fno-exceptions -fno-rtti`），否则产物和运行时开销都会膨胀；标准库只用头文件子集或 libc++ 的裁剪构建。最小应用实测 281 字节（C，`-nostdlib -O2`）。C++ 的实际体积尚未测量。

**Rust**：走 A 档，`wasm32-wasip1` 或 `wasm32-unknown-unknown`，`panic=abort`，`opt-level=z`。本机未安装该 target，体积未测。

**Go**：走 B 档 sidecar，用原生 Go 构建，不编 WASM。实测一个最小 Go 应用编成 wasip1 是 1,642,824 字节，剥符号后 gzip 仍有 492,130 字节，多出来的是一整份 GC 与调度器。同一逻辑的 C 产物是 281 字节，差约 5,800 倍。Go 的 SDK 是一个从同一份 IDL 生成的 RPC 客户端包，不是手写实现。

**Python**：走 B 档 sidecar，MicroPython 或 CPython 视内存预算。产物体积、启动时间、GIL 与 Host 调用的串行化行为都未实测。在测出来之前，不把它列进 v1 支持范围。

**JS**：QuickJS，A 档或 B 档待定。

**构建配方要进 CI。** 每种语言的示例应用都要在 CI 里构建并跑同一套 conformance 用例，否则"支持某语言"只是一句声明。

## 13. 兼容性：承认组合问题

应用版本、宿主版本、SDK 版本、贡献类型版本、权限模型版本、运行时版本叠加，确实是组合爆炸。不假装能全测。

做法是收敛维度并抽样。

- 引入一个**平台版本元组** `platform = (host, sdk, contribSchema, permModel)`，应用只声明 `minHost` 与 `sdk` 两个兼容字段，其余由宿主元组决定。
- 支持策略是 **N-1**：宿主支持当前与上一个 SDK 主版本，更早的拒绝安装并给出升级提示。
- 安装时做静态兼容检查，运行时做一次握手校验，两者都失败即拒绝。
- 发布时跑一个**抽样矩阵**：每个运行时的最新两版 SDK × 当前宿主 × 当前与上一贡献 schema，其余组合不承诺。抽样矩阵的结果要归档，未覆盖的组合明确标注"未验证"。
- 升级前做一次"贡献 schema 迁移演练"，即用旧版贡献数据在新宿主上加载一次，失败则不允许升级。

组合问题不能消除，只能把承诺范围写清楚。

## 14. 纵切计划：先证明最关键的假设

在扩展任何类型之前，只做一条最小纵切，跑通全生命周期。它的目的是证伪，不是演示。

**范围**

- 一个运行时：WASM，宿主先选一个（WAMR 或 wasmtime，按目标板的内存与构建复杂度二选一，选型标准写进 ADR）。
- 一种贡献：`telemetry.points`，只读。
- 最小能力：`tags.read` 单点位，`log`。无写、无告警、无 UI。
- 一个语言：C。C++ 与 Rust 在纵切通过后加入构建矩阵。

**必须跑通的路径**

1. 打包并签名一个只读应用。
2. 安装：签名、schema、SDK、配额校验通过；能力进入待批准状态。
3. 批准：管理员授予单点位只读；审计记录批准人。
4. 启动：WASM 实例运行，订阅一个点位，日志可见。
5. 越权：尝试读未授权点位，返回 `denied` 并写审计。
6. 故障：死循环触发 fuel/epoch 中断，实例标记 `faulted`，宿主进程存活。
7. 超限：分配超过 `heapKb`，实例失败，宿主不受影响。
8. 崩溃：kill 掉 app-host 进程，supervisor 拉起，应用按开机恢复策略重新激活。
9. 升级：安装新版本，健康检查通过后切换，旧版本保留。
10. 回滚：新版本激活失败，回退到旧版本，贡献一致。
11. 卸载：贡献标 `retired`，点位保留只读，UI 与北向不再出现。
12. 掉电：在提交与激活之间断电，重启后注册表状态自洽，没有半套贡献。

**验收标准**：以上 12 条在目标板上全部通过，且每条都有日志或测试作为证据。任何一条失败，先修机制，不扩范围。

只有这条纵切通过，第 9 节的贡献类型才逐个放开；第 11 节的一致性矩阵才逐个填；Python 与 Go 才进入正式支持列表。

## 15. 后续阶段（按触发条件，不按时间表）

## 16. 反例与取舍

**不做 VS Code 式特权扩展。** 应用在宿主主进程跑任意 JS，等于放弃隔离。

**不做 VS Code 式单扩展宿主。** 所有应用挤在一个进程，一个死循环拖垮全部。本文的 A 档仍是共享 app-host 进程，但用实例级中断与故障策略把影响限制在单实例，并明确登记了"宿主进程崩溃会带走全部 WASM 应用"这一残余风险。

**不手写多语言 SDK。** 用一份 WIT 生成绑定，避免语义漂移。

**不做 iPhone 式自带 UI。** 每个应用一套前端，WebUI 会碎成十个风格，权限与审计无法统一。

**不做 OSGi。** 动态加载 C 共享库在嵌入式网关上体积与 ABI 稳定性都不划算。

**不默认每应用一个进程。** 几十个应用会吃光内存。只有需要原生能力的语言进 B 档，并有进程数上限与 LRU。

**不把注册表做成可执行钩子。** 贡献是数据，不是回调。

**不把"声明"当"授权"。** 见第 7 节。

## 17. 未决与风险

- 注册表跨组件事务没有实现，也没有故障注入测试。掉电、激活失败、补偿失败三种路径都未验证。
- WASM 中断在目标运行时上的实际抢占延迟未测。用 fuel 还是 epoch 取决于运行时选型。
- app-host 进程是共享故障域。supervisor 重启能否在可接受时间内恢复全部应用，未测。
- Go sidecar 的 RPC 往返、冷启动、进程数上限对内存的影响，都未测。
- Python 的运行行为完全未验证，不列入 v1。
- 贡献 schema 的版本迁移没有演练过，升级路径可能比设想更脆。
- 权限点的生成与 `role-presets.yaml` 的构建期展开机制如何对齐，尚未定案。
- 组合兼容性只能抽样，未覆盖组合必须标注"未验证"，不能默认可用。
